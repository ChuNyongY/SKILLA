## 초록

대형 언어 모델(Large Language Model, LLM)을 이용한 PC 에이전트는 자연어 요청을 해석하고 운영체제의 기능을 호출할 수 있다. 그러나 같은 작업을 반복할 때도 실행 계획을 매번 새로 만들면 호출 수와 토큰 사용량이 누적되고, 이전 실패에서 확인된 예외 처리 방법이 다음 실행에 남지 않는다. 본 연구는 Windows에서 수행한 반복 작업의 절차, 판단 기준, 동적 입력과 완료 확인 방법을 스킬(skill)로 저장하고, 실행 기록을 이용해 새 버전의 개정 후보를 만드는 SKILLA를 구현하였다.

SKILLA의 스킬은 임의 코드나 현재 파일명을 저장하지 않는다. 다음 실행에도 적용할 수 있는 작업 순서와 규칙만 보관하며, 경로와 파일 수 같은 값은 실행 시점에 다시 확인한다. 검증된 스킬만 실행 계획에 제공하고, 스킬이 허용하지 않은 기능은 사용할 수 없게 하였다. 파일 이동이나 프로그램 실행은 별도의 검증기가 실제 Windows 상태를 다시 읽어 성공 여부를 판정한다. 실패 기록으로 만든 개정안은 초안 상태로 저장되며 사용자가 승인해야 활성화된다.

스킬 제공 방식의 영향을 확인하기 위해 스킬 없음(SK0), 일반 지침(SK1), 최초 스킬(SK2), 개정 스킬(SK3)의 네 조건을 비교하였다. 개발 단계 자료는 다섯 작업, 32개 완전 대응 블록, 128개 관측으로 구성하였다. 별도 확인 실험은 같은 다섯 작업을 세 번씩 반복하여 15개 블록, 60개 관측을 수집하였다. 확인 실험에서 SK0, SK1, SK2, SK3의 성공 횟수는 각각 10회, 12회, 12회, 14회였다. SK3의 평균 실행 시간은 12.367초로 SK0보다 34.2%, SK1보다 33.6%, SK2보다 52.0% 짧았다. 평균 토큰 수도 SK3가 가장 적었다. 다만 SK3와 각 기준 조건의 성공률 차이는 Holm 보정 뒤 유의수준 0.05에서 통계적으로 유의하지 않았다.

결과 차이는 파일을 분류하고 여러 번 이동하는 작업에서 주로 나타났다. 폴더 목록 조회와 Explorer 폴더 열기처럼 단순한 작업은 모든 조건이 성공했다. 개정 스킬은 반복 판단이 필요한 작업에서 계획 비용을 줄일 가능성을 보였지만, 한 대의 개발 PC에서 개발자가 실행한 소규모 결과이므로 일반 사용자 성능으로 확대할 수 없다. 본 연구의 결과는 스킬의 생성, 검색, 실행 기록, 개정과 독립 검증을 하나의 Windows 실행 하네스(harness)로 연결하고, 그 효과를 동일 모델과 동일 초기 상태에서 비교할 수 있는 구현 및 실험 절차를 제시한 데 있다.

## 1. 서론

### 1.1 연구 배경

PC 에이전트는 사용자의 자연어 요청을 실행 가능한 단계로 바꾸고 파일 시스템, 응용 프로그램과 웹 브라우저를 조작한다. 사용자는 명령 형식이나 프로그램별 메뉴를 외우지 않아도 되지만, 언어 모델은 같은 요청에도 다른 계획을 만들 수 있다. 현재 화면과 파일 상태가 달라지면 이전에 성공한 계획을 그대로 실행할 수도 없다. 실행 결과를 언어 모델의 답변만으로 판단하면 실제 파일이 이동하지 않았는데도 성공으로 기록하는 문제가 생긴다.

반복 작업에서는 이 문제가 더 분명하다. 예를 들어 “이번 주 과제 자료를 정리해 줘”라는 요청은 파일 찾기, 과목 판단, 폴더 이동과 결과 확인을 거친다. 다음 주에는 파일명과 개수가 바뀌지만 분류 기준과 확인 방법은 반복된다. 계획 전체를 매번 다시 생성하면 동일한 판단에 호출과 토큰을 다시 사용한다. 반대로 과거 파일명과 경로까지 고정하면 환경이 바뀌었을 때 잘못된 대상을 처리한다.

본 연구는 바뀌지 않는 작업 방법과 실행 때마다 바뀌는 값을 분리하였다. 반복되는 절차와 판단 기준은 스킬에 저장하고, 파일명과 경로는 실행 직전에 다시 관찰한다. 성공과 실패는 실제 운영체제 상태로 확인하며, 반복 실패가 확인되어도 기존 스킬을 자동으로 덮어쓰지 않고 개정 초안을 만든다.

### 1.2 연구 목적

연구 목적은 스킬의 생성·검색·재사용·개정이 가능한 Windows PC 에이전트를 구현하고, 스킬 제공 방식이 동일한 언어 모델의 실행 결과에 미치는 영향을 측정하는 것이다. 권한 분류와 사용자 승인은 연구의 최종 목적이 아니라 스킬을 실제 PC에서 안전하게 평가하기 위한 실행 기반으로 사용하였다.

본 연구에서 실행 하네스는 언어 모델 자체가 아니라 요청 분석, 스킬 검색, 계획 형식 검사, 권한 확인, 기능 실행, 결과 검증과 기록을 연결한 프로그램 구조를 뜻한다. 같은 언어 모델도 어떤 하네스를 사용하는지에 따라 볼 수 있는 정보, 호출할 수 있는 기능과 실패 후 행동이 달라진다. 따라서 모델 성능과 시스템 성능을 구분하려면 모델과 도구를 고정하고 하네스의 스킬 제공 방식만 바꾸어야 한다.

### 1.3 논문 구성

2장은 도구 사용 에이전트, PC 조작 에이전트와 경험 재사용 연구를 정리한다. 3장은 연구 질문과 범위를 제시한다. 4장과 5장은 SKILLA의 스킬 계약, 실행 하네스와 구현 내용을 설명한다. 6장은 네 조건의 대응 비교와 무결성 검증 방법을 제시한다. 7장은 개발 단계 자료와 별도 확인 실험을 구분해 보고한다. 8장은 결과의 의미와 한계를 다루고, 9장에서 결론을 정리한다.

## 2. 이론적 배경과 관련 연구

### 2.1 언어 모델의 추론과 도구 사용

ReAct는 언어 모델의 추론 과정과 외부 환경에 대한 행동을 번갈아 수행하는 방식을 제안하였다. 언어 모델이 관찰 결과를 다음 판단에 반영한다는 점은 PC 에이전트의 기본 반복 구조와 같다. Toolformer는 모델이 어떤 응용 프로그램 인터페이스(API)를 언제, 어떤 인자로 호출할지 학습할 수 있음을 보였다. 두 연구는 언어 모델이 답변 생성에 머물지 않고 외부 기능과 연결될 수 있다는 근거를 제공한다.

SKILLA는 모델 학습 방법을 제안하지 않는다. 모델이 생성한 행동을 미리 등록된 Windows 기능으로 제한하고, 각 기능의 입력 형식과 완료 조건을 프로그램에서 검사한다. 연구 대상은 모델 가중치가 아니라 모델 주변의 실행 구조와 스킬 정보다.

### 2.2 실행 경험과 스킬 재사용

Reflexion은 실행 결과를 자연어 피드백으로 저장하여 이후 시도에 사용하는 방법을 제안하였다. Voyager는 Minecraft 환경에서 실행 가능한 코드 형태의 스킬 라이브러리를 만들고, 환경 피드백과 오류를 이용해 스킬을 개선하였다. 이들 연구는 모델을 다시 학습하지 않고도 이전 실행의 경험을 다음 행동에 반영할 수 있음을 보여준다.

SKILLA의 스킬은 실행 코드를 보관하지 않는다는 점에서 Voyager의 코드 스킬과 다르다. 스킬에는 작업 절차, 동적 입력, 판단 규칙, 검증 규칙과 허용 기능 목록이 들어간다. 실제 실행은 등록된 기능을 통해서만 이루어진다. 개정안도 즉시 사용하지 않고 초안으로 보관하여 사람이 승인한 버전만 검색 대상으로 삼는다.

### 2.3 PC 조작 에이전트와 평가

UFO는 Windows 응용 프로그램을 관찰하고 제어하는 다중 에이전트 구조를 제시하였다. OSWorld는 Windows, macOS와 Ubuntu의 실제 응용 프로그램을 포함하는 작업 환경과 실행 기반 평가 방법을 제공하였다. AgentBench도 상호작용 환경에서 언어 모델 에이전트의 추론과 의사결정을 정량 평가하였다. 이 연구들은 최종 답변의 문장 품질보다 환경에서 목표 상태가 만들어졌는지를 측정해야 한다는 점을 공통적으로 보여준다.

SKILLA는 범용 화면 조작 성능보다 개인 Windows PC의 제한된 기능과 반복 작업을 연구 범위로 정하였다. 각 작업은 초기 상태를 다시 만들 수 있어야 하며, 실행기와 분리된 판정 방법이 있어야 한다. 이 범위는 지원 기능의 수를 줄이지만 조건별 결과를 같은 초기 상태에서 비교할 수 있게 한다.

### 2.4 기존 JARVIS 계열과의 차이

공개된 JARVIS 계열 프로젝트는 호출어, 음성 인식, 로컬 언어 모델, 웹 검색과 다양한 PC 기능을 결합하여 개인 비서의 기능 폭을 넓히는 경우가 많다. SKILLA도 음성과 텍스트 명령을 받을 수 있지만, 본 연구의 독립변수는 음성 인식이나 도구 수가 아니다. 반복 절차를 구조화해 저장하고, 검색된 정확한 버전과 실행 결과를 연결하며, 실패 기록으로 만든 개정안을 다시 검증하는 과정이 중심이다.

기존 프로젝트보다 항상 빠르거나 기능이 많다고 주장하지 않는다. SKILLA의 차이는 같은 모델·도구·초기 상태에서 스킬 제공 방식만 바꾼 대응 실험을 수행하고, 성공 여부를 파일과 앱 상태로 판정한다는 데 있다.

## 3. 연구 질문과 연구 범위

### 3.1 연구 질문

연구 질문은 다음과 같다.

- 연구 질문 1: 반복 작업의 절차와 규칙을 스킬로 제공하면 스킬이 없는 조건보다 작업 성공률이 달라지는가?
- 연구 질문 2: 스킬 재사용은 실행 시간, 언어 모델 호출 수와 토큰 사용량을 줄이는가?
- 연구 질문 3: 실패 기록을 반영한 개정 스킬은 최초 스킬보다 성공률과 실행 비용이 개선되는가?
- 연구 질문 4: 스킬의 영향은 파일 정리와 단순 조회 등 작업 유형에 따라 다르게 나타나는가?

성능 향상은 사전에 가정하지 않았다. 짧은 작업에서는 스킬 검색과 지침 추가로 실행 비용이 늘 수 있고, 잘못 검색되거나 오래된 스킬은 성공률을 낮출 수 있다.

### 3.2 연구 범위

평가 대상은 Windows 11 한 대에서 독립 판정이 가능한 다섯 작업으로 제한하였다. 과제 파일 정리, PDF 열기, 폴더 파일 목록 확인, 확장자별 정리와 Explorer 폴더 열기다. 이메일 전송, 결제, 영구 삭제와 같이 되돌리기 어렵거나 외부 사용자에게 영향을 주는 기능은 실험에서 제외하였다.

음성 입력 경로는 프로그램에 포함되어 있지만 이번 실험은 명령 문장의 차이를 줄이기 위해 텍스트 입력을 사용하였다. 그러므로 결과는 음성 인식률이나 호출어 탐지 성능을 설명하지 않는다. 사용자 만족도와 장시간 사용성도 측정하지 않았다.

## 4. 시스템 설계

### 4.1 전체 구조

SKILLA의 실행 흐름은 사용자 요청, 요청 분석, 스킬 검색, 계획 생성, 정책 검사, 실행, 독립 검증과 기록의 순서로 구성된다. 실행이 끝나면 결과와 비용이 사용한 스킬 ID 및 버전에 연결된다. 반복 실패 기준을 충족한 경우에는 새 개정 초안을 만들 수 있지만 기존 버전의 상태는 자동으로 바뀌지 않는다.

| 구성 요소 | 역할 |
|---|---|
| 사용자 인터페이스 | 텍스트·음성 요청 입력, 결과와 승인 요청 표시 |
| 요청 분석기와 계획기 | 목표와 필요한 입력을 파악하고 형식화된 계획 생성 |
| 스킬 관리기 | 검증된 스킬 검색, 버전과 상태 관리 |
| 기능 등록부 | 실행 가능한 Windows 기능과 입력 계약 관리 |
| 정책·승인 모듈 | 위험도에 따른 실행 허용과 정확한 행동 승인 |
| 실행기 | 파일, 앱과 시스템 기능 실행 |
| 결과 검증기 | 실제 파일·프로세스·창 상태로 완료 여부 판정 |
| 실행 기록·개정 모듈 | 성공·실패·비용 기록과 개정 초안 생성 |

### 4.2 스킬 계약

스킬은 제목과 호출 표현, 반복 절차, 동적 입력, 판단 규칙, 검증 규칙, 허용 기능 목록과 버전 상태로 구성된다. 예를 들어 과제 자료 정리 스킬은 “파일 찾기 → 과목 판단 → 과목별 폴더로 이동 → 결과 확인”이라는 순서를 저장한다. 이번 주 파일명, 파일 수와 현재 폴더는 저장하지 않고 매번 다시 읽는다.

스킬 상태는 DRAFT, VERIFIED, RETIRED로 나뉜다. DRAFT는 생성 또는 개정된 초안이며 실행 검색에서 제외된다. 사용자가 내용을 확인하고 승인한 버전만 VERIFIED가 된다. 새 버전이 활성화되면 이전 버전은 RETIRED로 남아 실행 기록을 추적할 수 있다.

### 4.3 최소 권한 실행

언어 모델은 운영체제 명령이나 임의 Python 코드를 직접 실행하지 않는다. 기능 등록부에 정의된 동작만 계획에 넣을 수 있다. 각 기능은 입력 형식, 최소 위험 등급과 완료 조건을 가진다. 스킬은 이 기능 목록을 더 넓힐 수 없으며, 등록부와 스킬 양쪽에서 허용한 기능만 실행된다.

사용자 승인이 필요한 행동은 대상, 인자, 위험도와 만료 시간에 결합된 승인 토큰을 사용한다. 다른 파일이나 다른 인자에 같은 승인을 재사용할 수 없다. 실행 직전에도 정책을 다시 검사하여 계획 이후 상태 변화에 대응한다.

### 4.4 독립 결과 검증

실행기의 성공 반환값은 최종 성공 판정으로 사용하지 않는다. 파일 이동은 출발지와 목적지, 파일 내용 또는 해시를 다시 확인한다. 프로그램 실행은 실행 파일의 등록 정보와 새 프로세스·창을 확인한다. 시스템 정보 조회는 필요한 항목의 존재와 형식을 검사한다. 이 구조는 언어 모델의 답변과 실제 PC 상태를 분리한다.

### 4.5 스킬 개정

개정 판단기는 최소 관측 수, 최근 성공률과 반복 실패 코드를 확인하여 KEEP, PROPOSE_REVISION 또는 INSUFFICIENT_EVIDENCE를 반환한다. 개정이 필요하다고 판단해도 자동으로 기존 스킬을 변경하지 않는다. 새 절차는 DRAFT로 저장되며 후보 비교와 사람 검토를 거친다. 개정 과정에서 허용 기능이 늘어나는 경우에는 자동 승인을 차단한다.

## 5. 프로그램 구현

### 5.1 실행 환경과 저장 구조

프로그램은 Python 기반 Windows 응용 프로그램으로 구현하였다. 스킬 카탈로그와 사용 기록은 로컬 SQLite에 저장한다. 실험 관측값은 중단 후 이어서 실행할 수 있는 추가 전용 JSONL 원장에 먼저 기록하고, 정해진 일정이 끝난 뒤 분석용 JSON으로 내보낸다. 각 결과 근거 파일은 SHA-256으로 관측값과 연결한다.

실행 계획은 기능 이름과 인자 형식이 고정된 자료 구조로 검사한다. 형식에 맞지 않는 계획, 등록되지 않은 기능과 스킬 범위를 벗어난 기능은 실행 전에 거부한다. NIM API를 사용하는 계획 호출은 호출 횟수와 입력·출력 토큰을 누적 기록하되 API 키와 사용자 파일 내용은 실험 자료에 넣지 않는다.

### 5.2 사용자 인터페이스

현재 사용자 인터페이스는 한국어 텍스트 명령 입력, 실행 결과 표시, 작업 중지, 작업 화면 선택, 스킬 관리와 스킬 후보 검토를 제공한다. 스킬 후보 검토 창은 주 창과 별도의 최상위 창으로 구현하여 목록이 비어 보이던 창 생성 결함을 수정하였다. 실행 결과 화면에는 언어 모델의 설명이 아니라 독립 검증된 시스템 정보와 작업 결과를 표시한다.

### 5.3 설치와 자동 시험

검증 시점의 프로그램 버전은 0.1.9다. 자동 시험은 1,096개 중 1,091개가 통과하고 5개가 건너뛰기 처리되었다. 정적 검사와 엄격한 자료형 검사도 통과하였다. 설치본에서 NIM 자격 증명 사전 점검, 13개 기능 조립, 시스템 정보 조회와 독립 검증을 확인하였다. 이 수치는 연구 효과가 아니라 구현 회귀를 확인한 결과다.

### 5.4 실험 수집과 무결성

실험 일정은 고정 난수 초기값으로 조건 순서를 섞은 뒤 블록마다 순환시킨다. 수집기는 다음 셀 하나만 실행기에 넘기고, 반환된 작업·반복·조건이 일정과 일치할 때만 원장에 기록한다. 같은 블록의 모델 설정, 도구 목록과 초기 상태 해시가 다르면 분석을 거부한다. 중간에 프로그램이 종료되어도 원장이 일정의 접두사인지 확인한 뒤 다음 셀부터 재개한다.

## 6. 실험 설계

### 6.1 비교 조건

| 조건 | 제공 정보 | 비교 목적 |

네 조건은 같은 모델 ID, 모델 설정, 기능 목록과 초기 파일 상태를 사용한다. 차이는 계획기에 제공한 스킬 정보뿐이다. 각 작업·반복 번호에 네 조건이 모두 있어야 하나의 완전 대응 블록으로 인정하였다.

### 6.2 평가 작업

| 작업 | 주요 행동 | 완료 판정 |

| PDF 열기 | 대상 PDF 검색, 등록 브라우저로 열기 | 대상 파일과 새 창 확인 |

### 6.3 측정 지표

주 지표는 독립 검증을 통과한 실행의 비율인 작업 성공률이다. Wilson 방식의 95% 신뢰구간을 함께 계산하였다. 보조 지표는 실행 시간, 언어 모델 호출 수, 입력·출력 토큰 합과 사용자 확인 횟수다. 실행 오류와 계획 오류도 실패로 포함하였다.

SK3와 SK0·SK1·SK2의 성공 여부는 같은 블록 안에서 대응시켜 정확 McNemar 검정을 수행하였다. 세 번의 비교에서 발생하는 다중 검정은 Holm 방법으로 보정하였다. 유의수준은 양측 0.05로 정하였다.

### 6.4 개발 자료와 확인 실험

개발 단계 자료는 32개 완전 대응 블록과 128개 관측으로 구성된다. 이 자료는 실행기와 스킬을 수정하는 과정에서 수집되었으므로 최종 확인 자료와 합치지 않았다.

별도 확인 실험은 결과를 보기 전에 실행 식별자 developer10, 난수 초기값 2026102001, 다섯 작업과 작업별 세 번 반복을 기록하였다. 총 15개 블록, 60개 관측이다. 각 조건 실행 전에 새 임시 폴더에 같은 초기 자료를 만들었다. 실패도 제외하지 않았다.

### 7.5 실패와 실행 기록 검증

실패는 12건이었다. 과제 파일 정리에서는 관찰 반복 횟수 소진과 계획 형식 오류가 발생하였다. 확장자별 정리에서는 관찰 루프 오류와 반복 횟수 소진이 발생했고, PDF 열기의 두 실패는 계획 형식 오류였다.

확인 실험 자료에는 60개 관측과 60개 결과 근거가 들어 있다. 근거 파일의 실제 SHA-256을 무결성 목록과 대조한 결과 불일치는 없었다. 다섯 실행기를 같은 인자로 다시 실행했을 때 원장, 관측과 보고서 15개 파일의 SHA-256은 바뀌지 않았다. 완료된 셀을 다시 실행하지 않고 기존 기록에서 재개했음을 확인하였다. 자료에서 Windows 사용자 절대경로와 NIM API 키 형식 문자열은 발견되지 않았다.

## 8. 논의

### 8.1 연구 질문별 해석

연구 질문 1에 대해 SK3는 확인 실험에서 가장 높은 성공률을 보였지만, 보정한 검정 결과는 유의하지 않았다. 표본 수가 작으므로 스킬이 성공률을 높였다고 확정할 수 없다. 관측된 차이는 후속 실험의 효과 크기와 표본 수를 정하는 자료로 사용할 수 있다.

연구 질문 2에 대해 SK3의 평균 실행 시간, 호출 수와 토큰 수는 다른 조건보다 적었다. 특히 최초 스킬인 SK2보다 시간과 토큰이 크게 줄었다. 구조화된 스킬을 제공하는 것만으로 비용이 줄지 않았고, 실패 원인을 반영한 개정 내용이 함께 필요했을 가능성이 있다.

연구 질문 3에 대해 SK3는 SK2보다 성공 횟수가 두 번 많고 평균 비용이 낮았다. 그러나 PDF 열기에서는 SK3가 한 번 더 실패했고 대응 성공률 차이도 유의하지 않았다. 개정 스킬은 항상 이전 버전보다 낫다고 볼 수 없다. 후보를 별도 시험한 뒤 사람이 승인하도록 한 설계가 필요한 이유다.

연구 질문 4에 대해 복수 파일의 분류·이동처럼 중간 판단과 확인이 반복되는 작업에서 차이가 컸다. 한 번의 조회나 창 열기로 끝나는 작업에서는 네 조건이 같았다. 스킬을 모든 요청에 적용하기보다 반복성과 판단 단계가 충분한 작업에 선택적으로 적용해야 한다.

### 8.2 실행 하네스가 모델 성능에 미치는 영향

언어 모델은 네 조건에서 같았지만 제공받은 정보와 실패 처리 규칙이 달랐다. SK0은 매번 절차를 구성해야 했고, SK1은 일반 문장 지침을 받았다. SK2와 SK3은 동적 입력, 판단 규칙과 완료 조건이 분리된 스킬을 받았다. 이 차이는 모델의 지식 자체를 바꾸지 않고도 계획 길이, 도구 선택과 반복 횟수에 영향을 주었다.

하네스는 모델의 능력을 새로 만드는 장치가 아니다. 모델이 사용할 수 있는 맥락을 정리하고 허용 행동을 제한하며 실제 결과를 다시 관찰하게 한다. 따라서 본 실험의 차이는 언어 모델 단독 성능이 아니라 모델과 하네스를 합친 시스템 성능이다.

### 8.3 제한점

첫째, 확인 실험은 개발자 한 명이 한 대의 Windows PC에서 수행한 15개 블록이다. 사용자 간 차이와 다른 하드웨어·응용 프로그램 환경을 반영하지 못한다. 둘째, 다섯 작업은 현재 기능으로 독립 판정이 가능한 범위에서 선택하였다. 이메일, 웹 양식과 여러 응용 프로그램을 오가는 긴 작업에는 결과를 적용할 수 없다.

셋째, 조건별 실행 시간이 API 응답 지연과 현재 PC 상태의 영향을 받을 수 있다. 대응 설계와 순서 균형화로 영향을 줄였지만 완전히 제거하지 못했다. 넷째, SK3의 확인 횟수가 가장 많아 자동화 비용 일부가 사용자에게 옮겨갔을 수 있다. 다섯째, 개발 자료와 확인 자료 모두 실제 참가자 연구가 아니며 개발자가 작성한 명령과 스킬을 사용하였다.

후속 연구에서는 연구윤리 절차를 확인한 뒤 여러 참가자의 반복 작업을 수집하고, 사전에 계산한 표본 수와 별도 시험 자료를 사용해야 한다. 작업 복잡도별로 스킬 검색의 이득과 손익분기 반복 횟수를 비교하고, 스킬을 쓰지 않는 편이 나은 요청을 판별하는 기준도 평가할 필요가 있다.

## 9. 결론

본 연구는 Windows 반복 작업의 절차와 판단 기준을 스킬로 저장하고, 검증된 버전을 재사용하며, 실행 기록으로 개정 초안을 만드는 SKILLA를 구현하였다. 스킬에는 실행 때마다 바뀌는 파일명과 경로를 넣지 않고, 실제 PC 상태를 다시 관찰하도록 하였다. 계획, 권한 확인, 실행과 결과 검증을 연결한 하네스는 임의 코드 실행을 막고 성공 판정을 운영체제 상태에 근거하게 한다.

별도 확인 실험에서 개정 스킬 조건은 15회 중 14회 성공했고 평균 실행 시간과 토큰 수가 가장 적었다. 차이는 여러 파일을 분류하고 이동하는 작업에서 주로 나타났다. 단순 조회와 폴더 열기에서는 스킬의 성공률 이점이 없었고, 통계 검정에서도 보정 후 유의한 비교가 없었다.

이 결과는 개정 스킬이 모든 PC 작업을 개선한다는 증거가 아니다. 프로그램과 실험 경로가 같은 조건을 재현하고 실제 결과로 평가할 수 있음을 확인한 개발자 실험이다. 다음 단계는 독립 참가자와 더 다양한 반복 작업을 사용하여 관측된 차이가 재현되는지 확인하는 것이다.
