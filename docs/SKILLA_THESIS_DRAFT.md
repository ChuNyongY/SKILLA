## 초록

대형 언어 모델(Large Language Model, LLM)은 많은 문장을 학습하여 사용자의 요청을 이해하고 답이나 실행 계획을 만드는 인공지능 모델이다. PC 에이전트는 이 모델의 계획을 파일·응용 프로그램 같은 컴퓨터 기능의 실행으로 연결하는 프로그램이다. 같은 작업의 계획을 매번 새로 만들면 모델 호출 수와 토큰 사용량이 누적된다. 토큰은 언어 모델이 요청과 응답을 처리할 때 세는 글자 조각 단위다. 본 연구는 반복 작업의 순서·판단 기준·완료 확인 방법을 스킬(skill)로 저장하고 다시 사용하는 로컬 인공지능 에이전트 SKILLA를 구현하였다. 여기서 스킬은 실행 코드를 뜻하지 않고, 반복해서 쓸 수 있도록 구조화한 작업 방법을 뜻한다. 로컬 에이전트라는 명칭은 스킬 저장, 음성 처리, Windows 기능 실행과 결과 검증이 사용자 PC에서 이루어지는 구조를 가리키며, 실행 계획 생성에는 NVIDIA NIM의 언어 모델 서비스를 사용한다.

SKILLA의 스킬에는 다음 실행에도 적용할 수 있는 작업 순서와 규칙을 보관한다. 경로·파일명·파일 수처럼 실행할 때마다 달라지는 동적 입력은 실행 직전에 다시 확인한다. 승인된 스킬과 미리 등록된 기능의 공통 범위 안에서 계획을 실행하고, 별도의 검증기가 실제 Windows 상태를 다시 읽어 성공 여부를 판정한다. 이처럼 실행기의 완료 보고와 별도로 결과를 확인하는 방식을 독립 검증이라고 한다. 실패 기록으로 만든 개정안은 초안으로 저장하고, 사용자가 내용을 확인한 뒤 활성화한다.

스킬 제공 방식의 영향을 확인하기 위해 스킬 없음(SK0), 일반 문장 지침(SK1), 최초 스킬(SK2), 실패 기록을 반영한 개정 스킬(SK3)을 비교하였다. 같은 작업과 반복 번호에서 네 조건을 모두 실행한 묶음을 완전 대응 블록이라고 한다. 관측 한 건은 한 조건에서 한 번 실행한 결과다. 개발 단계 자료는 다섯 작업, 32개 블록, 128개 관측으로 구성하였다. 별도 확인 실험은 같은 다섯 작업을 세 번씩 반복하여 15개 블록, 60개 관측을 수집하였다. 확인 실험에서 SK0, SK1, SK2, SK3의 성공 횟수는 각각 10회, 12회, 12회, 14회였다. SK3의 평균 실행 시간은 12.367초로 SK0보다 34.2%, SK1보다 33.6%, SK2보다 52.0% 짧았고 평균 토큰 수도 가장 적었다. 여러 비교에서 우연한 판정 오류를 줄이는 Holm 보정을 적용한 p값은 0.375, 1.000, 1.000이었다. p값은 조건 차이가 없다는 가정에서 현재 이상의 차이가 나타날 확률이며, 세 값 모두 판단 기준인 0.05보다 컸다.

결과 차이는 파일을 분류하고 여러 번 이동하는 작업에서 주로 나타났고, 폴더 목록 조회와 Windows 파일 탐색기(Explorer) 폴더 열기는 모든 조건이 성공했다. 본 확인 실험은 개발 PC 한 대에서 개발자 한 명이 수행한 15개 블록으로 구성된다. 구현 결과는 스킬의 생성·검색·재사용·개정과 독립 검증을 하나의 실행 하네스(harness)로 연결한다. 실행 하네스는 요청 분석, 모델 호출, 스킬 검색, 기능 실행, 결과 검증과 기록의 순서를 관리하는 제어 프로그램이다. 본 연구는 이 하네스에서 모델과 초기 상태를 고정하고 스킬 제공 방식만 바꾸어 결과를 비교하였다.

## 1. 서론

### 1.1 연구 배경

PC 에이전트는 사용자의 자연어 요청을 실행 가능한 단계로 바꾸고 파일 시스템, 응용 프로그램과 웹 브라우저를 조작한다. 언어 모델은 같은 요청에도 다른 계획을 만들 수 있고, 현재 화면과 파일 상태도 실행할 때마다 달라진다. 실행 결과를 모델의 답변만으로 판단하면 실제 파일 상태와 성공 기록이 어긋날 수 있다.

반복 작업에서는 이 문제가 더 분명하다. 예를 들어 “이번 주 과제 자료를 정리해 줘”라는 요청은 파일 찾기, 과목 판단, 폴더 이동과 결과 확인을 거친다. 다음 주에는 파일명과 개수가 바뀌지만 분류 기준과 확인 방법은 반복된다. 계획 전체를 매번 다시 생성하면 동일한 판단에 호출과 토큰을 다시 사용한다. 반대로 과거 파일명과 경로까지 고정하면 환경이 바뀌었을 때 잘못된 대상을 처리한다.

본 연구는 반복되는 작업 방법과 실행할 때마다 바뀌는 값을 분리하였다. 절차와 판단 기준은 스킬에 저장하고, 파일명과 경로는 실행 직전에 다시 관찰한다. 성공과 실패는 실제 운영체제 상태로 확인하며, 반복 실패가 확인되면 기존 버전을 보존한 채 개정 초안을 만든다.

### 1.2 연구 목적

연구 목적은 스킬의 생성·검색·재사용·개정이 가능한 Windows PC 에이전트를 구현하고, 스킬 제공 방식이 동일한 언어 모델의 실행 결과에 미치는 영향을 측정하는 것이다. 권한 분류와 사용자 승인은 연구의 최종 목적이 아니라 스킬을 실제 PC에서 안전하게 평가하기 위한 실행 기반으로 사용하였다.

본 연구에서 실행 하네스는 요청 분석, 스킬 검색, 계획 형식 검사, 권한 확인, 기능 실행, 결과 검증과 기록을 연결하는 제어 프로그램을 뜻한다. 같은 언어 모델도 하네스가 제공하는 정보·기능·실패 처리 규칙에 따라 실행 결과가 달라진다. 실험에서는 모델과 도구를 고정하고 하네스가 제공하는 스킬 정보만 바꾸어 시스템 차이를 측정하였다.

### 1.3 논문 구성

2장은 도구 사용 에이전트, PC 조작 에이전트와 경험 재사용 연구를 정리한다. 3장은 연구 질문과 범위를 제시한다. 4장과 5장은 SKILLA의 스킬 계약, 실행 하네스와 구현 내용을 설명한다. 6장은 네 조건의 대응 비교와 무결성 검증 방법을 제시한다. 7장은 개발 단계 자료와 별도 확인 실험을 구분해 보고한다. 8장은 결과의 의미와 한계를 다루고, 9장에서 결론을 정리한다.

## 2. 이론적 배경과 관련 연구

### 2.1 언어 모델의 추론과 도구 사용

ReAct(Reasoning and Acting, 추론과 행동)는 언어 모델이 판단한 내용을 행동으로 옮기고, 그 결과를 관찰하여 다음 판단에 반영하는 방법이다. 즉, 추론·행동·관찰을 한 번으로 끝내지 않고 목표를 달성할 때까지 반복한다. 이러한 구조는 PC 에이전트가 기능을 실행한 뒤 실제 컴퓨터 상태를 다시 확인하는 과정과 연결된다. Toolformer는 언어 모델이 외부 도구를 호출할 시점과 호출에 넣을 값을 스스로 학습하도록 만든 방법이다. 여기서 도구는 계산기, 검색 기능, 응용 프로그램 인터페이스(Application Programming Interface, API)처럼 모델 밖에서 실제 기능을 수행하는 수단을 뜻한다. API는 프로그램끼리 정해진 형식으로 요청과 결과를 주고받는 접속 규칙이다. 두 연구는 언어 모델의 판단을 외부 기능 실행과 연결하는 방법을 제시한다.

SKILLA는 학습이 끝난 언어 모델을 사용하며, 연구 대상은 모델의 학습값인 가중치보다 모델 주변의 실행 구조와 스킬 정보다. 모델이 만든 계획은 미리 등록된 Windows 기능과 입력 형식에 맞는지 검사한 뒤 실행한다.

### 2.2 실행 경험과 스킬 재사용

Reflexion은 실패 원인과 개선 내용을 자연어 피드백으로 기록하고 다음 시도의 판단 자료로 사용하는 자기 성찰 방법이다. 모델의 가중치를 다시 학습하는 대신 이전 시도의 언어 기록을 다음 입력에 제공한다. Voyager는 가상 환경에서 스스로 목표를 정하고, 성공한 작업 코드를 스킬 라이브러리에 저장하여 다음 작업에서 검색·재사용하는 에이전트다. Voyager는 Minecraft 환경에서 실행 결과와 오류를 이용해 저장된 스킬을 확장하였다. 이들 연구는 모델을 다시 학습하지 않고도 이전 실행의 경험을 다음 행동에 반영할 수 있음을 보여준다.

Voyager는 실행 가능한 코드를 스킬로 저장한다. SKILLA는 작업 절차, 동적 입력, 판단 규칙, 검증 규칙과 허용 기능 목록을 스킬로 저장하고 실제 동작은 등록된 기능이 담당한다. 개정안은 초안으로 보관하며, 사람이 승인한 버전을 검색 대상으로 삼는다.

### 2.3 PC 조작 에이전트와 평가

UFO(UI-Focused Agent, 사용자 화면 중심 에이전트)는 Windows 화면과 응용 프로그램의 조작 대상을 파악하고 작업을 나누어 수행하는 다중 에이전트 구조다. 다중 에이전트는 역할이 다른 여러 에이전트가 하나의 작업을 분담하는 방식을 뜻한다. OSWorld는 Windows, macOS와 Ubuntu의 실제 응용 프로그램에서 컴퓨터 조작 에이전트를 시험하는 평가 환경이다. 에이전트가 만든 문장이 아니라 작업 뒤의 실제 운영체제 상태로 성공 여부를 판정한다. AgentBench는 언어 모델 에이전트가 여러 상호작용 환경에서 내린 판단과 수행 결과를 같은 기준으로 비교하는 평가 체계다. 이 연구들은 최종 답변의 문장 품질보다 환경에서 목표 상태가 만들어졌는지를 측정해야 한다는 점을 공통적으로 보여준다.

SKILLA는 범용 화면 조작 성능보다 개인 Windows PC의 제한된 기능과 반복 작업을 연구 범위로 정하였다. 각 작업은 초기 상태를 다시 만들 수 있어야 하며, 실행기와 분리된 판정 방법이 있어야 한다. 이 범위는 지원 기능의 수를 줄이지만 조건별 결과를 같은 초기 상태에서 비교할 수 있게 한다.

### 2.4 기존 JARVIS 계열과의 차이

공개된 JARVIS 계열 프로젝트는 호출어, 음성 인식, 로컬 언어 모델, 웹 검색과 다양한 PC 기능을 결합하여 개인 비서의 기능 폭을 넓히는 경우가 많다. SKILLA도 음성과 텍스트 명령을 받을 수 있지만, 본 연구의 독립변수는 음성 인식이나 도구 수가 아니다. 반복 절차를 구조화해 저장하고, 검색된 정확한 버전과 실행 결과를 연결하며, 실패 기록으로 만든 개정안을 다시 검증하는 과정이 중심이다.

SKILLA의 차이는 기능의 수보다 반복 작업 방법의 저장·버전 관리·재사용·개정에 있다. 같은 모델·도구·초기 상태에서 스킬 제공 방식만 바꾼 대응 실험을 수행하고, 성공 여부를 파일과 응용 프로그램 상태로 판정하였다.

## 3. 연구 질문과 연구 범위

### 3.1 연구 질문

연구 질문은 다음과 같다.

- 연구 질문 1: 반복 작업의 절차와 규칙을 스킬로 제공하면 스킬이 없는 조건보다 작업 성공률이 달라지는가?
- 연구 질문 2: 스킬 재사용은 실행 시간, 언어 모델 호출 수와 토큰 사용량을 줄이는가?
- 연구 질문 3: 실패 기록을 반영한 개정 스킬은 최초 스킬보다 성공률과 실행 비용이 개선되는가?
- 연구 질문 4: 스킬의 영향은 파일 정리와 단순 조회 등 작업 유형에 따라 다르게 나타나는가?

실험은 스킬 제공 방식에 따른 성공률과 실행 비용의 변화 방향을 모두 측정하도록 설계하였다. 짧은 작업에서는 스킬 검색과 지침 추가가 실행 비용으로 작용할 수 있으며, 검색된 스킬의 내용과 현재 환경의 일치 여부도 성공 결과에 영향을 준다.

### 3.2 연구 범위

평가 대상은 Windows 11 한 대에서 결과를 독립 판정할 수 있는 다섯 작업이다. 과제 파일 정리, PDF 열기, 폴더 파일 목록 확인, 확장자별 정리와 Explorer 폴더 열기를 사용하였다. 각 작업은 실행 전 초기 상태를 복원할 수 있고, 파일·프로세스·창 상태로 완료 여부를 확인할 수 있다.

SK0~SK3 비교 실험은 조건마다 같은 명령 문장을 제공하기 위해 텍스트 입력을 사용하였다. 음성 경로는 실제 사용자 발화 네 건으로 별도 기능 검사를 수행하였다. 음성을 글자로 바꾸고, 신규 스킬 후보 표시와 음성 승인, 등록·실행·독립 검증까지 이어지는 흐름을 확인하였다. 음성 검사의 범위는 네 발화의 전사 결과와 기능 연결 상태다.

## 4. 시스템 설계

### 4.1 전체 구조

SKILLA의 실행 흐름은 사용자 요청, 요청 분석, 스킬 검색, 계획 생성, 정책 검사, 실행, 독립 검증과 기록의 순서로 구성된다. 실행이 끝나면 결과와 비용이 사용한 스킬 ID 및 버전에 연결된다. 반복 실패 기준을 충족한 경우에는 새 개정 초안을 만들 수 있지만 기존 버전의 상태는 자동으로 바뀌지 않는다.

| 구성 요소 | 역할 |
|---|---|
| 사용자 인터페이스 | 텍스트·음성 요청 입력, 결과와 승인 요청 표시 |
| 요청 분석기와 계획기 | 목표와 필요한 입력을 파악하고 형식화된 계획 생성 |
| 스킬 관리기 | 검증된 스킬 검색, 버전과 상태 관리 |
| 기능 등록부 | 실행 가능한 Windows 기능과 입력 계약 관리 |
| 정책·승인 모듈 | 위험도에 따른 실행 허용과 정확한 행동 승인 |
| 실행기 | 파일, 앱과 시스템 기능 실행 |
| 결과 검증기 | 실제 파일·프로세스·창 상태로 완료 여부 판정 |
| 실행 기록·개정 모듈 | 성공·실패·비용 기록과 개정 초안 생성 |

### 4.2 스킬 계약

스킬은 제목과 호출 표현, 반복 절차, 동적 입력, 판단 규칙, 검증 규칙, 허용 기능 목록과 버전 상태로 구성된다. 예를 들어 과제 자료 정리 스킬은 “파일 찾기 → 과목 판단 → 과목별 폴더로 이동 → 결과 확인”이라는 순서를 저장한다. 이번 주 파일명, 파일 수와 현재 폴더는 저장하지 않고 매번 다시 읽는다.

스킬 상태는 DRAFT(검토 전 초안), VERIFIED(사용자가 승인한 활성 버전), RETIRED(사용이 끝난 이전 버전)로 나뉜다. 검색기는 VERIFIED 상태만 실행 계획에 제공한다. 새 버전이 활성화되면 이전 버전은 RETIRED로 보존하여 과거 실행 기록과 사용 버전을 추적한다.

### 4.3 최소 권한 실행

기능 등록부는 프로그램이 실행할 수 있는 동작과 입력 형식, 최소 위험 등급, 완료 조건을 정리한 목록이다. 언어 모델의 계획은 등록부와 스킬 양쪽에서 허용한 기능으로 한정되며, 실제 실행은 기능별 실행기가 담당한다.

사용자 승인이 필요한 행동은 대상·인자·위험도·만료 시간을 묶어 만든 승인 토큰을 사용한다. 여기서 승인 토큰은 특정 동작에 대한 사용자 확인을 프로그램이 식별하는 일회성 자료다. 실행 직전에도 정책을 다시 검사하여 계획 이후의 상태 변화를 반영한다.

### 4.4 독립 결과 검증

독립 검증기는 실행기의 완료 보고와 별도로 실제 상태를 확인한다. 파일 이동은 출발지·목적지와 파일 내용 또는 해시를, 프로그램 실행은 등록된 실행 파일과 새 프로세스·창을, 시스템 정보 조회는 필수 항목과 자료 형식을 검사한다. 해시는 파일 내용으로 계산한 고정 길이 값으로, 두 파일의 내용이 같은지 확인하는 데 사용한다.

### 4.5 스킬 개정

개정 판단기는 최소 관측 수, 최근 성공률과 반복 실패 코드를 확인하여 KEEP(현행 유지), PROPOSE_REVISION(개정 후보 생성) 또는 INSUFFICIENT_EVIDENCE(판단 자료 부족)를 반환한다. 새 절차는 DRAFT로 저장하고 후보 비교와 사람 검토를 거친다. 허용 기능이 늘어나는 개정안은 사용자의 별도 확인 대상으로 표시한다.

## 5. 프로그램 구현

### 5.1 실행 환경과 저장 구조

프로그램은 Python 기반 Windows 응용 프로그램으로 구현하였다. 개발 PC는 Windows 11 Home, AMD Ryzen 5 9500F 6코어 12스레드, 메모리 15.4GB, NVIDIA GeForce RTX 5060 Ti로 구성하였고 주 화면은 2560×1440 해상도를 사용하였다. 스킬 카탈로그와 사용 기록은 한 개의 파일로 자료를 관리하는 로컬 데이터베이스 SQLite에 저장한다. 실험 관측값은 한 줄에 한 건의 JSON 자료를 기록하는 JSONL 원장에 먼저 추가하고, 일정이 끝난 뒤 분석용 JSON 파일로 내보낸다. 각 결과 근거 파일은 SHA-256 해시 함수로 계산한 값과 관측값을 연결하여 내용 변경 여부를 확인한다.

요청을 계획으로 바꾸는 대형 언어 모델은 NVIDIA NIM(NVIDIA가 모델 실행을 API 형태로 제공하는 서비스)의 `z-ai/glm-5.3-flash`를 사용한다. 음성을 글자로 바꾸는 음성 인식(Speech-to-Text, STT)은 사용자 PC에서 실행하는 Whisper large-v3-turbo(`dropbox-dash/faster-whisper-large-v3-turbo`, CPU int8)를 사용한다. int8은 모델 계산값을 8비트 정수로 표현하여 메모리 사용량과 CPU 실행 부담을 줄이는 방식이다. 글자를 음성으로 읽는 음성 합성(Text-to-Speech, TTS)은 사용자 PC에서 실행하는 Supertonic 3 int8(`sherpa-onnx`)을 사용한다. Windows 기본 음성 합성은 Supertonic 3의 초기화 오류에 대비한 대체 경로다. NIM 전송 범위는 계획 생성을 위한 요청문과 도구 정의이며, 음성 원본과 사용자 파일은 로컬 실행기가 처리한다.

실행 계획은 기능 이름과 인자 형식이 고정된 자료 구조로 검사한다. 형식 오류, 미등록 기능, 스킬 허용 범위 밖의 기능은 실행 전에 차단한다. NIM API 계획 호출은 호출 횟수와 입력·출력 토큰을 누적 기록하며, 인증 정보와 사용자 파일 내용은 관측 항목에서 분리한다.

### 5.2 사용자 인터페이스

현재 사용자 인터페이스는 한국어 텍스트·음성 명령 입력, 대기·계획·실행 상태 표시, 작업 중지, 작업 화면 선택, 스킬 관리와 스킬 후보 검토를 제공한다. 마이크 입력 크기는 주 화면의 반응 표시기에 실시간으로 나타나며, 인식한 명령은 계획 단계에서 다시 보여 준다. 스킬 후보 검토 창은 주 창과 별도의 최상위 창으로 구현하여 목록이 비어 보이던 창 생성 결함을 수정하였다. 실행 결과 화면에는 언어 모델의 설명이 아니라 독립 검증된 시스템 정보와 작업 결과를 표시한다.

음성 경로는 호출 문장과 명령을 인식한 뒤 텍스트 명령과 같은 계획·정책·실행·검증 경로에 넘긴다. 실제 사용자 음성 네 건은 의도한 문장으로 전사되었다. 빈 스킬 저장소에서 신규 등록 후보 생성, 음성 승인, 버전 1 등록, 시스템 정보 조회와 독립 검증까지 한 흐름으로 완료하였다. 이 검사는 음성 입력에서 스킬 등록과 실행으로 이어지는 기능 연결을 대상으로 하였다.

### 5.3 설치와 자동 시험

검증 시점의 프로그램 버전은 0.1.9다. 2026년 11월 5일 재배치 감사 기록에서 자동 시험 1,157개 중 1,152개가 통과했고, 하드웨어·운영체제 상태가 필요한 시험 5개는 건너뛰기 처리되었다. 프로그램을 실행하기 전에 문법과 코드 규칙을 확인하는 정적 검사와 변수·함수의 자료형 일치를 확인하는 엄격한 자료형 검사도 통과하였다. 같은 감사에서 배포 폴더 1,868개 파일의 해시가 배포 목록과 일치하여 파일 무결성을 확인하였다. 무결성은 저장·이동 과정에서 파일 내용이 바뀌지 않은 상태를 뜻한다. NIM 인증 정보 사전 점검, 13개 등록 기능의 로딩과 연결, 시스템 정보 조회와 독립 검증도 확인하였다. 이 항목들은 프로그램 구현 상태와 이전 결함의 재발 여부를 검사한 결과다.

### 5.4 실험 수집과 무결성

실험 일정은 고정 난수 초기값으로 조건 순서를 섞은 뒤 블록마다 순환시킨다. 수집기는 다음 셀 하나만 실행기에 넘기고, 반환된 작업·반복·조건이 일정과 일치할 때만 원장에 기록한다. 같은 블록의 모델 설정, 도구 목록과 초기 상태 해시가 다르면 분석을 거부한다. 중간에 프로그램이 종료되어도 원장이 일정의 접두사인지 확인한 뒤 다음 셀부터 재개한다.

## 6. 실험 설계

### 6.1 비교 조건

| 조건 | 제공 정보 | 비교 목적 |
|---|---|---|
| SK0 | 스킬 없이 모델과 Windows 기능만 제공 | 기본 실행 성능 |
| SK1 | 반복 절차를 일반 지침으로 제공 | 단순 프롬프트 저장 효과 |
| SK2 | 구조화한 최초 스킬 제공 | 검색·구조·버전 관리 효과 |
| SK3 | 실패 기록을 반영한 개정 스킬 제공 | 개정의 추가 효과 |

네 조건은 같은 모델 식별자, 모델 설정, 기능 목록과 초기 파일 상태를 사용한다. 계획기에 제공하는 스킬 정보만 조건에 따라 바꾸었다. 각 작업·반복 번호에 네 조건이 모두 포함된 묶음을 하나의 완전 대응 블록으로 정하였다. 이 설계는 같은 작업에서 조건별 결과를 짝지어 비교하여 작업 난이도 차이의 영향을 줄인다.

### 6.2 평가 작업

| 작업 | 주요 행동 | 완료 판정 |
|---|---|---|
| 과제 파일 정리 | 파일 확인, 과목 분류, 여러 파일 이동 | 과목별 목적 폴더와 파일 내용 확인 |
| PDF 열기 | 대상 PDF 검색, 등록 브라우저로 열기 | 대상 파일과 새 창 확인 |
| 폴더 파일 목록 확인 | 지정 폴더 읽기 | 현재 파일명과 개수 확인 |
| 확장자별 파일 정리 | 확장자 판단, 여러 파일 이동 | 확장자별 목적 폴더 확인 |
| Explorer 폴더 열기 | 등록된 Explorer 새 창 실행 | 정확한 폴더의 새 창 확인 |

### 6.3 측정 지표

주 지표는 독립 검증을 통과한 실행의 비율인 작업 성공률이다. 성공률의 불확실한 범위를 나타내기 위해 소표본 이항비율에 사용할 수 있는 Wilson 방식의 95% 신뢰구간을 함께 계산하였다. 이 구간은 같은 실험을 반복했을 때 계산 절차가 참 성공률을 포함하는 구간을 약 95%의 비율로 만들도록 구성한 범위다. 보조 지표는 실행 시간, 언어 모델 호출 수, 입력·출력 토큰 합과 사용자 확인 횟수다. 실행 오류와 계획 오류도 실패로 집계하였다.

SK3와 SK0·SK1·SK2의 성공 여부는 같은 블록 안에서 짝지어 정확 McNemar 검정을 수행하였다. 정확 McNemar 검정은 두 조건의 성공·실패가 서로 달라진 블록 수를 이용해 대응된 이항 결과의 차이를 평가한다. 세 비교를 함께 수행할 때 우연한 차이를 유의하다고 판단할 가능성이 커지는 문제는 Holm 방법으로 p값을 보정하였다. p값은 조건 차이가 없다는 가정 아래 현재와 같거나 더 큰 차이가 관측될 확률이며, 판단 기준인 유의수준은 양측 0.05로 정하였다.

### 6.4 개발 자료와 확인 실험

개발 단계 자료는 32개 완전 대응 블록과 128개 관측으로 구성된다. 실행기와 스킬 수정에 사용한 개발 자료와 수정이 끝난 뒤 수집한 확인 자료는 역할에 따라 분리해 보고하였다.

별도 확인 실험은 결과 확인 전에 실행 식별자 `developer10`, 난수 초기값 `2026102001`, 다섯 작업과 작업별 세 번 반복을 기록하였다. 난수 초기값은 조건 실행 순서를 같은 규칙으로 다시 만들기 위한 숫자다. 총 15개 블록, 60개 관측이며 각 조건 실행 전에 새 임시 폴더에 같은 초기 자료를 만들었다. 실패와 계획 오류를 포함한 모든 예정 실행을 집계하였다.

## 7. 실험 결과

### 7.1 개발 단계 결과

### 7.5 실패와 실행 기록 검증

실패는 12건이었다. 과제 파일 정리에서는 관찰 반복 횟수 소진과 계획 형식 오류가 발생하였다. 확장자별 정리에서는 관찰 루프 오류와 반복 횟수 소진이 발생했고, PDF 열기의 두 실패는 계획 형식 오류였다.

확인 실험 자료에는 60개 관측과 60개 결과 근거가 들어 있다. 근거 파일의 실제 SHA-256을 무결성 목록과 대조한 결과 불일치는 없었다. 다섯 실행기를 같은 인자로 다시 실행했을 때 원장, 관측과 보고서 15개 파일의 SHA-256은 바뀌지 않았다. 완료된 셀을 다시 실행하지 않고 기존 기록에서 재개했음을 확인하였다. 자료에서 Windows 사용자 절대경로와 NIM API 키 형식 문자열은 발견되지 않았다.

## 8. 논의

### 8.1 연구 질문별 해석

연구 질문 1에서 SK3는 15회 중 14회 성공하여 네 조건 중 가장 높은 성공률을 기록했다. Holm 보정 p값은 모든 비교에서 0.05보다 컸다. 관측된 성공률 차이와 불일치 쌍의 수는 후속 실험의 표본 수를 설계하는 기초 자료로 사용할 수 있다.

연구 질문 2에서 SK3의 평균 실행 시간, 호출 수와 토큰 수는 다른 조건보다 적었다. 특히 SK2와 비교하면 평균 실행 시간은 52.0%, 평균 토큰 수는 44.8% 적었다. 이 실험에서 최초 스킬과 개정 스킬 사이의 차이는 실패 기록을 반영한 절차와 완료 규칙이었다.

연구 질문 3에서 SK3는 SK2보다 두 번 더 성공하고 평균 실행 시간과 토큰 수가 적었다. 작업별로는 PDF 열기에서 SK3가 한 번 실패하여 변화 방향이 같지 않았다. 이에 따라 SKILLA는 개정 후보를 기존 버전과 분리해 시험하고 사용자가 결과를 확인한 뒤 활성화하도록 구성하였다.

연구 질문 4에 대해 복수 파일의 분류·이동처럼 중간 판단과 확인이 반복되는 작업에서 차이가 컸다. 한 번의 조회나 창 열기로 끝나는 작업에서는 네 조건이 같았다. 스킬을 모든 요청에 적용하기보다 반복성과 판단 단계가 충분한 작업에 선택적으로 적용해야 한다.

### 8.2 실행 하네스가 모델 성능에 미치는 영향

언어 모델은 네 조건에서 같았지만 제공받은 정보와 실패 처리 규칙이 달랐다. SK0은 매번 절차를 구성해야 했고, SK1은 일반 문장 지침을 받았다. SK2와 SK3은 동적 입력, 판단 규칙과 완료 조건이 분리된 스킬을 받았다. 이 차이는 모델의 지식 자체를 바꾸지 않고도 계획 길이, 도구 선택과 반복 횟수에 영향을 주었다.

하네스는 모델에 제공할 작업 정보와 허용 행동을 정하고, 실행 결과를 다시 관찰하여 다음 단계와 성공 판정에 반영한다. 본 실험에서 측정한 값은 같은 언어 모델과 서로 다른 스킬 제공 조건을 결합한 시스템의 실행 결과다.

### 8.3 제한점

확인 실험 자료는 개발자 한 명이 한 대의 Windows PC에서 수행한 15개 블록이다. 평가 작업은 현재 기능으로 초기 상태를 복원하고 결과를 독립 판정할 수 있는 다섯 종류로 구성하였다. 따라서 본 결과가 직접 설명하는 범위는 이 개발 환경과 다섯 작업이다.

조건별 실행 시간에는 NIM API 응답 지연과 당시 PC 상태가 함께 포함된다. 실험은 네 조건을 같은 블록에서 실행하고 조건 순서를 순환하여 시간대와 작업 차이를 분산하였다. SK3의 사용자 확인 횟수는 평균 1.0회로 가장 많아 시간·토큰 감소와 확인 부담이 함께 나타났다. 명령과 스킬은 개발자가 작성했으며, 사람 간 사용성 차이는 후속 참가자 실험에서 측정할 항목이다.

후속 연구에서는 연구윤리 절차를 확인한 뒤 여러 참가자의 반복 작업을 수집하고, 사전에 계산한 표본 수와 별도 시험 자료를 사용해야 한다. 작업 복잡도별로 스킬 검색의 이득과 손익분기 반복 횟수를 비교하고, 스킬을 쓰지 않는 편이 나은 요청을 판별하는 기준도 평가할 필요가 있다.

## 9. 결론

본 연구는 Windows 반복 작업의 절차와 판단 기준을 스킬로 저장하고, 승인된 버전을 재사용하며, 실행 기록으로 개정 초안을 만드는 SKILLA를 구현하였다. 파일명과 경로 같은 동적 입력은 실행 직전에 다시 관찰한다. 계획, 권한 확인, 실행과 결과 검증을 연결한 하네스는 등록 기능을 통해 작업을 수행하고 운영체제 상태를 근거로 성공을 판정한다.

별도 확인 실험에서 개정 스킬 조건은 15회 중 14회 성공했고 평균 실행 시간과 토큰 수가 가장 적었다. 차이는 여러 파일을 분류하고 이동하는 작업에서 주로 나타났다. 단순 조회와 폴더 열기는 모든 조건이 성공했고, 성공률 비교의 Holm 보정 p값은 0.375, 1.000, 1.000이었다.

본 결과는 개발 PC 한 대, 개발자 한 명, 다섯 작업과 15개 완전 대응 블록에서 얻었다. 같은 초기 상태를 복원하고 실제 결과 근거로 조건을 비교하는 실험 경로가 재현되었다. 다음 단계에서는 독립 참가자와 다양한 반복 작업을 추가하여 사용자 간 차이와 작업 범위에 따른 효과를 측정한다.
