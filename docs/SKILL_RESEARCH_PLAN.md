# Windows 반복 작업용 AI 스킬 연구 기준

최종 갱신: 2026-10-16

## 연구 목적

이 프로젝트의 핵심 연구 대상은 권한 분류 자체가 아니라 **AI 스킬의 생성, 검색, 재사용,
실행 결과 기록, 개정과 재사용**이다. 권한·위험도·승인·실행 후 검증은 스킬의 효과를 실제
Windows 상태로 측정하고 잘못된 실행을 제한하는 공통 실행 기반이다.

연구 질문은 다음과 같다.

> 같은 LLM, 같은 Windows 도구, 같은 초기 상태와 실행 예산에서 작업 절차를 스킬로 저장해
> 재사용하면 스킬이 없는 경우나 단순 저장 지침을 제공한 경우보다 성공률과 반복 실행 비용이
> 개선되는가? 실패 기록을 반영한 개정 스킬은 초기 스킬보다 나은가?

성능 향상은 가정하지 않는다. 짧은 작업에서는 검색과 스킬 입력 비용 때문에 더 느리거나 비쌀 수
있고, 오래된 스킬이나 잘못 검색된 스킬은 성공률을 낮출 수 있다.

## 스킬에 저장하는 정보

스킬은 실행 코드나 현재 파일명을 저장하지 않는다. 다음 실행에서도 재사용할 방법만 저장한다.

- 작업 이름과 설명
- 호출 표현과 선택 조건
- 반복되는 작업 절차
- 실행할 때마다 다시 확인할 동적 입력
- 분류와 예외 처리에 사용하는 판단 규칙
- 완료 여부를 확인하는 검증 규칙
- 사용할 수 있는 등록 capability 목록
- 버전과 상태

파일명, 파일 개수, 현재 경로, 파일 내용, 실행 중인 앱 상태와 예외 상황은 매 실행 시 다시
관찰한다. 스킬은 이 값을 고정된 과거 값으로 대체하지 않는다.

## 실행 흐름

```text
사용자 요청
  -> 요청 분석
  -> VERIFIED 스킬 검색
  -> 있으면 절차·판단 규칙·검증 규칙을 현재 입력에 적용
  -> 없으면 일반 계획 생성
  -> Windows 실행
  -> 실제 파일·앱 상태로 결과 검증
  -> 성공/실패와 비용 기록
  -> 충분한 실패 근거가 있으면 개정 후보 제안
  -> 사용자 승인 뒤 새 버전 활성화
```

개정 판단은 스킬을 자동 변경하는 권한이 아니다. 시스템은 관측 수, 성공률과 반복 실패 코드를
근거로 `KEEP`, `PROPOSE_REVISION`, `INSUFFICIENT_EVIDENCE` 중 하나만 제안한다. 새 절차는 항상
DRAFT로 만들고 사용자가 승인한 뒤에만 VERIFIED가 된다.

## 주 실험 조건

기존 안전 하네스의 B0/B1/P1/P2 명칭과 섞이지 않도록 스킬 연구 조건은 SK0~SK3으로 기록한다.

| 조건 | 제공 정보 | 확인하려는 효과 |
|---|---|---|
| SK0 | 스킬 없음 | 같은 모델과 도구의 기본 성능 |
| SK1 | 동일 내용을 일반 저장 지침으로 제공 | 단순 프롬프트 저장 효과 |
| SK2 | 최초 검증 스킬 제공 | 검색·구조화·버전 관리가 추가한 효과 |
| SK3 | 실패 기록을 반영한 개정 스킬 제공 | 개정이 추가한 효과 |

각 참가자·작업·반복 번호에는 네 조건의 관측이 모두 있어야 한다. 일부 조건만 있는 블록은 최종
비교에서 제외하는 대신 입력 오류로 거부한다.

`build-skill-study-schedule`은 고정 seed로 최초 조건 순서를 섞은 뒤 블록마다 순환시키는 방식으로
SK0~SK3의 실행 순서를 균형화한다. 같은 seed는 같은 순서를 재현한다. 각 대응 블록은 모델 ID,
모델 설정 SHA-256, 도구 표면 SHA-256과 초기 상태 SHA-256이 네 조건에서 정확히 같아야 한다.
하나라도 달라지면 스킬 효과와 환경 차이를 분리할 수 없으므로 `analyze-skill-study`가 거부한다.
각 결과에는 독립 결과 증거 SHA-256도 필수로 기록한다.

`SkillStudyCollector`는 정해진 일정의 다음 셀 하나만 runner에 전달하고, 반환된 참가자·작업·반복·조건이
일정과 정확히 일치할 때만 append-only JSONL ledger에 `fsync`한다. 중단 후에는 ledger가 일정의 정확한
접두사인지 확인해 이어서 실행한다. 전체 일정이 끝나기 전에는 분석용 JSON 배열로 내보내지 않는다.
따라서 일부 조건만 성공한 블록을 실수로 최종 분석에 포함하는 것을 수집 단계와 분석 단계에서 모두
차단한다.

## 측정값

- 작업 성공률: 미리 정한 파일 위치·파일 hash·앱 상태와 실제 결과가 일치한 비율
- 실행 시간: 요청 시작부터 결과 검증 종료까지의 시간
- LLM 호출 수
- 입력 토큰과 출력 토큰
- 사용자 추가 확인 횟수
- 실행 비용
- 스킬 생성·검증 비용과 개정·재검증 비용

성공률은 조건별 점 추정치만 쓰지 않고 Wilson 방식의 양측 95% 신뢰구간을 함께 보고한다. 개정 스킬
SK3와 SK0·SK1·SK2의 성공 여부는 같은 참가자·작업·반복 블록 안에서 대응시키고, 정확 McNemar
검정으로 비교한다. 세 비교의 다중 검정은 Holm 방식으로 보정한다. 표본이 작을 때 p값이 유의하지
않더라도 효과가 없다고 단정하지 않고 성공률 차이·신뢰구간·표본 수를 함께 보고한다.

비용은 다음처럼 분리한다.

```text
스킬 누적 비용(n회)
  = 생성·검증 비용 + 개정·재검증 비용 + n × 스킬 사용 실행 비용

기본 방식 누적 비용(n회)
  = n × 스킬 없는 실행 비용
```

스킬 실행 1회당 절감액이 0 이하이면 손익분기 반복 횟수가 존재하지 않는다. 절감액이 양수일 때만
초기 준비 비용을 절감액으로 나눠 올림한 값을 손익분기 반복 횟수로 보고한다.

## 실험 작업

우선 구현 범위는 현재 Windows adapter로 결과를 독립 검증할 수 있는 작업으로 제한한다.

1. 주간 과제 자료를 과목별 폴더로 분류하고 이동
2. 이름이나 위치가 달라진 관련 PDF를 찾아 열기
3. 다운로드 자료를 파일 형식과 규칙에 따라 정리
4. 지정된 폴더의 현재 파일 이름을 읽기 전용으로 확인
5. 허용된 하위 폴더를 등록된 Windows Explorer 새 창으로 열고 정확한 창을 확인·정리

스킬 생성 사례와 최종 평가 사례는 분리한다. 최종 평가에서는 파일명, 파일 수, 경로, 후보 수와
프로그램 실행 상태를 바꾼다. 모든 조건은 같은 초기 snapshot 또는 같은 fixture 복원 상태에서
시작한다.

## 추가 개발자 검증 batch 사전 고정

결과를 확인하기 전에 참가자 묶음 `developer09`, seed `2026101609`를 고정했다. 파일 정리,
PDF 열기, 폴더 목록, 확장자 정리와 Explorer 폴더 열기 다섯 작업을 각각 3회 반복하고 모든
작업에서 SK0~SK3 완전 대응 블록을 수집한다.

중단되면 기존 append-only ledger에서 재개한다. 일부 조건만 있는 불완전 블록은 분석하지 않으며,
실패 관측도 제외하지 않는다. 이는 특정 작업에서 유의성을 만들기 위한 선택 수집이 아니고 사용자
참가자 연구를 대신하지 않는다.

이 batch는 2026-10-16 완료됐다. 기존 유효 자료와 합치면 완전 대응 32블록·128관측이다.
SK0 26/32, SK1 24/32, SK2 30/32, SK3 32/32였고 SK3 대 SK1만 Holm 보정 p값
0.0234375로 이 묶음 안에서 0.05보다 작았다. SK0 비교는 0.0625, SK2 비교는 0.5다. 실제 참가자
표본이 아니므로 일반적 성능 결론으로 사용하지 않는다.

구현됨:

- SQLite 로컬 스킬 카탈로그와 DRAFT/VERIFIED/RETIRED 버전 수명주기
- 검증된 스킬 검색과 capability 허용 목록 결합
- 동적 입력, 판단 규칙과 검증 규칙을 포함한 스킬 계약
- 스킬이 없을 때 일반 계획으로 진행하는 경로
- 결과, 시간, LLM 호출, 토큰과 사용자 개입 기록
- 관측 수·성공률·반복 실패 코드 기반 개정 필요성 판정
- SK0~SK3 완전 대응 블록과 비용 손익분기를 검사하는 분석 모델
- 독립 검증된 성공 trace에서 엄격한 JSON 스킬 초안을 생성하는 LLM 작성기
- 반복 실패 또는 성공률 기준을 충족할 때만 개정 초안을 만드는 정책 결합
- 생성·개정 초안의 자동 활성화 차단과 개정 시 capability 권한 확대 차단
- 원문 인자·경로·문서 내용을 제외한 실행 근거 계약과 근거 SHA-256
- 상시 실행 결과를 개인정보 최소화 trace로 변환해 로컬 검토 대기열에 넣는 제품 연결
- 사용자가 명시적으로 선택한 trace 한 건만 NIM에 보내 DRAFT를 만드는 CLI 동의 경계
- 재현 가능한 SK0~SK3 순서 균형화 일정과 모델·설정·도구·초기 상태 동일성 검사
- 엄격한 관측 JSON 로더와 대응 블록 조건별 평균 분석 CLI
- 일정 일치성을 검사하고 중단 후 이어받는 append-only 실험 수집 ledger
- 조건별 성공률 95% 신뢰구간과 SK3 대응 성공 비교·Holm 보정
- NIM 응답 usage 기반 누적 호출·성공·입출력 토큰·usage 누락 계측
- 동일한 파일 fixture를 매 조건마다 새 임시 폴더에 복원하고, SK0~SK3 context만 바꾸어 실제 NIM,
  실행기와 독립 완료 probe를 거치는 1블록 파일럿 수집 도구
- 조건별 결과를 즉시 append-only ledger에 저장하고 중단 시 다음 cell부터 재개하며, 완료 후 관측
  JSON과 분석 보고서를 원자적으로 내보내는 실행 경로
- 기존 스킬과 개정 후보를 최소 3개 동일 환경 대응 trial로 비교해 성공 회귀, 개별 성공→실패,
  평균 시간·토큰 허용 비율 초과를 거부하는 후보 평가 관문. 통과 상태도 자동 승인이 아니라
  `READY_FOR_HUMAN_REVIEW`로만 표시한다.
- 카탈로그에서 기존 `VERIFIED`와 이를 직접 대체하는 다음 버전 `DRAFT`를 정확히 결합하고, 블록마다
  기존/후보 실행 순서를 교차한 뒤 측정값의 스킬 ID·버전·블록 결합을 확인하는 후보 수집 조립부.
  평가 완료 후에도 카탈로그 상태를 바꾸지 않는다.
- 파일 정리 v1/v2를 실제 카탈로그·NIM·실행기·독립 probe와 연결하는 3-block 후보 runner. 조건별
  근거 파일, 재개 가능한 원장, trial export와 평가 report를 생성한다.
- 같은 스킬 버전의 최근 실행에 모델 구성·도구 표면 SHA-256을 결합하고, 근거 부족·반복 실패·환경
  변화를 구분하는 오래된 스킬 감지. 날짜만으로 판정하거나 스킬 상태를 자동 변경하지 않는다.
- 운영과 동일한 검색기로 라벨 자료의 정확도·거짓 양성·거짓 음성·잘못된 스킬·모호 판정을 집계하고,
  동점이면 스킬을 임의 선택하지 않는 검색 평가기와 CLI.
- 결과를 본 뒤 수정하지 않은 한국어 요청 22건, 별도 VERIFIED 스킬 7개, 배타적 출력과 입력·결과·
  카탈로그 SHA-256을 사용하는 재현 가능한 검색 파일럿 runner.
- 제품이 선택한 정확한 스킬 버전을 LLM Plan 밖의 일회성 task 결합에 보존하고, 실행 종료 시
  성공·실패·중단·처리 시간·모델/도구 지문을 자동 사용 기록으로 남기는 폐루프 연결.
- 계획 직전·직후 NIM 누적 계측값의 직렬화된 차이로 스킬별 계획 호출·입출력 토큰을 결합하고,
  usage 누락·계측 미지원을 완전한 0으로 오해하지 않게 하는 품질 표시.

2026-10-14 고정 개발자료 최초 검색에서는 22건 중 18건을 맞혔다. 한 글자 토큰 제외와 등록 어휘에
한정한 한국어 조사 제거를 구현한 뒤 19건을 맞혔다. 변경 전에 별도로 고정한 보류자료 25건에서는
14건에서 21건으로 바뀌었고 거짓 양성은 전후 모두 0건이었다. 변경 후에도 거짓 음성 1, 잘못 선택 1,
모호 판정 2가 남았다. 보류자료는 결과 확인 후 추가 튜닝에 쓰지 않는다. 모두 개발자가 작성한 소규모
검색 경로 시험이므로 사용자 참여 검색 성능을 대신하지 않는다.

2026-10-14 근거 파일을 포함한 실제 1블록 파일럿에서 SK0 0/1, SK1 0/1, SK2 1/1, SK3 1/1을
관측했다. SK3는 16,839 ms·NIM 2회·3,353-token, SK2는 28,185 ms·2회·3,180-token이었다.
SK0과 SK1은 각각 33,678 ms·3회·5,360-token, 71,744 ms·5회·10,458-token 후 실패로 닫혔다. 네 조건의 모델 설정,
도구 표면과 경로 독립 초기 상태 hash가 같음을 수집기가 확인했다. 성공한 두 조건은 각각 YELLOW
승인 2회를 거쳤다. 표본이 하나뿐이라 모든 McNemar p-value와 Holm 보정값은 1.0이며, 이 결과로
효율 향상이나 통계적 우월성을 주장하지 않는다.

각 조건의 `outcome_evidence_sha256`은 별도 evidence JSON의 실제 파일 SHA-256과 일치한다. SK3와
SK2는 2-round 완료 및 두 번의 `PREPARED -> COMMITTED`, SK0은 실행 전 `PlannerError`, SK1은
3-round 예산 소진과 이동 0건을 기록했다. 앞선 근거 파일 없는 파일럿은 구현 smoke로만 보존하며
두 실행은 코드 버전과 식별자가 같으므로 독립 연구 표본으로 합치지 않는다.

같은 날 실제 카탈로그의 초기 v1과 개정 v2를 3개 대응 block으로 추가 비교했다. 실행 순서는
v1→v2, v2→v1, v1→v2로 교차했다. v1은 0/3, v2는 3/3이며 평균 시간은 53,342.7 ms에서
31,196.3 ms로 41.5%, 평균 token은 8,395.3에서 6,349.7로 24.4% 감소했다. 여섯 evidence hash가
실제 파일과 일치했고 v2의 모든 이동 journal은 두 번의 `PREPARED -> COMMITTED`였다. 이 결과는
개정 후보를 사람 검토 대상으로 올릴 근거이며, 표본 3개·단일 작업이므로 논문의 일반적 효율 결론이나
통계적 우월성 주장이 아니다. 후보는 평가 후에도 DRAFT다.

두 번째 작업으로 hash-pinned PDF를 등록 Edge 새 창에서 여는 SK0~SK3 1블록을 실행했다. 네 조건
모두 1/1 성공했고 호출 수는 각각 1회였다. 시간은 SK0 12,445 ms, SK1 6,143 ms, SK2 5,887 ms,
SK3 10,517 ms였으며 token은 각각 1,511, 1,538, 1,574, 1,612였다. 네 조건의 PDF·viewer·새 창
검증과 창 종료가 성공했고 evidence hash가 일치했다. SK0도 성공했으므로 성공률 차이는 0이다. 단순
작업에서는 스킬 이득이 없을 수 있다는 반례이며, 표본 1개라 시간·token 우열은 해석하지 않는다.

두 작업을 하나의 자기완결형 근거 묶음으로도 검증했다. 통합 기술통계는 SK0 1/2, SK1 1/2,
SK2 2/2, SK3 2/2 성공이고 평균 시간은 각각 23,061.5, 38,943.5, 17,036.0, 13,678.0 ms다.
평균 token은 3,435.5, 5,998.0, 2,377.0, 2,482.5다. 모든 evidence hash가 일치했지만 작업마다
한 블록뿐이고 세 성공 비교의 Holm 보정 p값이 모두 1.0이므로 기술통계 외 결론을 내리지 않는다.
