# SKILLA 확장 가능성 우선순위와 범위 판단

상태: 조사·판단 전용, 기능 미구현

작성일: 2026-11-18

## 판단 기준

확장 아이디어는 다음 기준으로 비교한다.

1. SKILLA의 핵심인 반복 작업의 저장·검색·재사용·개정과 직접 연결되는가
2. 실제 Windows 상태를 독립적으로 검증할 수 있는가
3. 사용자의 불편을 줄이는 효과가 분명한가
4. 개인정보와 외부 서비스 의존성을 제한할 수 있는가
5. 현재 코드의 capability·정책·승인·검증 구조를 그대로 사용할 수 있는가

단순히 대화가 가능하거나 앱을 많이 열 수 있다는 이유만으로 우선순위를 높이지 않는다. 저장된 작업
방법을 다시 사용하고 실행 결과를 검증할 수 있을 때 SKILLA의 확장으로 본다.

## 현재 이미 있는 기반

- 음성·텍스트 입력과 로컬 STOP
- 로컬 Whisper STT와 Supertonic TTS
- 스킬 저장·검색·승인·재사용·실패 기반 개정 후보
- capability별 정책·승인·실행·독립 검증
- 전경 프로그램 감지와 스킬 제안
- 요일·시각 예약과 실행 전 사용자 확인
- 실행 시점에 달라지는 동적 입력 창
- Google 검색 열기
- Chrome 기록에서 최근·자주 방문한 YouTube 후보를 골라 등록 Chrome 새 창으로 열기
- SQLite 상태 백업·복원과 강제 종료 뒤 WAL 복구 시험

YouTube 기능은 페이지가 정확한 새 창으로 열렸는지까지 검증한다. 실제 재생·소리 출력 상태는 아직
검증하지 않는다. 대화 `RESPOND` 경로는 분류만 하며 답변 생성기는 없다.

## 확장 후보 비교

| 후보 | 핵심 주제 적합도 | 현재 기반 | 남은 핵심 작업 | 단독 예상 기간 | 우선순위 |
|---|---|---|---|---:|---|
| 원격 관측값 최소화 | 필수 기반 | 15개 허용 projection·task-local 파일 handle·전송 직전 재검사 | 파일명 필요 작업의 로컬 분류·확인 UI | 1~3일 | P0 |
| 실제 장시간 음성·절전 복구 | 필수 기반 | 가속 8시간·모의 장치 복구 통과 | 실제 8시간, 장치 분리, 절전·잠금 시험 | 3~5일 | P0 |
| 고정 자기소개·도움말 | 보조 인터페이스 | 음성·텍스트·TTS | 정체성 카드, 로컬 route, STOP 연결 | 1~3일 | P1 |
| 실제 음악 재생 확인 | 높음 | Chrome 기록 선택·새 창 검증 | Native Messaging 또는 로컬 플레이어, 재생 상태 검증 | 7~10일 | P1 |
| 로컬 일상대화 | 중간 | RESPOND 분류, 로컬 TTS | 로컬 모델 시험, 원격 전 분리, 최근 문맥 | 1~2주 | P1 |
| 동의 기반 사용자 선호 기억 | 중간 | 제한형 memory와 SQLite | 별도 DB, DPAPI, 목록·수정·삭제·만료 UI | 1~2주 | P1 |
| 상황별 작업 묶음 추천 | 높음 | 전경 앱·예약 제안과 동적 입력 | 여러 신호 결합, 중복 억제, 추천 설명 | 1~2주 | P1 |
| 실패 원인별 자동 복구 스킬 | 매우 높음 | 제한 재시도·장치 fallback·개정 기록 | 오류별 복구 계약, 중복 효과 차단, 검증 | 기능당 2~4일 | P1 |
| 문서 정리·요약 스킬 | 높음 | 파일 목록·이동·PDF 열기 기반 | 로컬 문서 추출, 민감정보 경계, 결과물 검증 | 2~4주 | P2 |
| 일정·메일 작업 연결 | 중간 | 메시지 규격 일부와 예약 기반 | 계정 연결, OAuth, 초안·전송 분리, 외부 결과 검증 | 2~4주 | P2 |
| 제3자 기능 묶음 SDK | 매우 높음 | registry·contract·executor·verifier 구조 | manifest 규격, 서명·권한, 격리 시험, 배포 도구 | 3~5주 | P2 |
| 화면 인식 기반 범용 조작 | 중간 | 제한된 UIA·화면 검증 연구 코드 | 화면 개인정보, 좌표 배제, 앱별 복구, 대규모 시험 | 4~8주 | P3 |
| 여러 PC 동기화 | 낮음 | 로컬 백업만 존재 | 암호화 동기화, 충돌·삭제 전파, 계정·서버 운영 | 6~10주 | P3 |

기간은 현재 코드와 개발자 1명을 기준으로 한 순차 작업 추정이다. 실제 사용자 시험, 서명 인증서,
외부 서비스 심사와 저사양 PC 확보 기간은 포함하지 않는다. 여러 항목을 동시에 시작하면 공통 경계를
중복 수정하게 되므로 기간을 단순 합산하거나 병렬로 줄일 수 없다.

## 권장 순서

### 1단계: 기존 제품 경계 완성

1. 원격 관측값 최소화의 남은 파일명 로컬 처리와 확인 UI
2. 실제 8시간 음성·절전·장치 변경 시험
3. 깨끗한 Windows 사용자 설치와 현재 안내문 포함 여부 확인

이 단계가 끝나기 전에는 사적인 대화와 선호 기억을 넣지 않는다.

### 2단계: 사용자가 바로 체감하는 작은 확장

1. 고정 자기소개·도움말
2. 실제 음악 재생 상태 확인
3. 상황별 작업 묶음 추천과 오류별 복구 스킬

세 기능 모두 현재 SKILLA의 실행·검증 구조를 재사용할 수 있고 시연 결과도 명확하다.

### 3단계: 대화와 유대감

1. 로컬 입력 분리기 60문장 시험
2. 로컬 대화 모델 30문장 시험
3. 최근 4~8턴의 세션 문맥
4. 동의 기반 선호 기억과 관리 화면
5. 실제 장시간 음성 대화와 삭제 반영 시험

고정 자기소개는 2단계에서 먼저 제공할 수 있지만 사용자 선호를 기억하는 기능은 3단계를 모두 거쳐야
한다.

### 4단계: 외부 업무와 개발자 생태계

문서, 일정·메일, 제3자 capability 묶음을 순서대로 검토한다. 외부 전송과 계정 권한이 생기므로 각
서비스마다 초안·실행·검증을 분리해야 한다.

## 아이디어별 구체적 예

### 상황별 작업 묶음

```text
수업 프로그램 감지
→ 사용자가 연결한 스킬 제안
→ 강의 폴더 열기
→ 메모장 열기
→ 현재 주차 자료 존재 확인
→ 결과 기록
```

프로그램 감지만으로 자동 실행하지 않고, 미리 허용한 낮은 위험 스킬 또는 사용자 승인을 거친 작업만
실행한다.

### 실패 복구 스킬

```text
과제 자료 정리 중 대상 폴더 없음
→ 오류 코드 확인
→ 허용 루트 안에서 대체 폴더 후보 확인
→ 사용자에게 후보 표시
→ 승인된 대상만 다시 실행
→ 이동 전후 파일 수와 원본 누락 검증
```

복구 과정도 스킬과 같은 capability 허용 목록 안에서만 수행한다.

### 실제 음악 재생

```text
"평소에 듣던 노래 틀어 줘"
→ 로컬 Chrome 기록 복사본에서 후보 선택
→ 선택 이유 표시
→ 전용 로컬 플레이어 또는 Chrome 연결로 열기
→ 재생 상태 PLAYING 확인
→ 소리가 나지 않으면 자동 재시도하지 않고 사용자 조작 안내
```

현재 구현은 `열림`까지만 검증하므로 `재생됨`이라고 표현하면 안 된다.

### 자기소개와 유대감

```text
"자기소개해 봐"
→ 로컬 고정 정체성 카드
→ 이름·역할·실행 원칙·기억 원칙 설명
→ 로컬 TTS

"내가 발라드를 좋아한다고 기억해 둬"
→ 허용 선호 key 확인
→ 저장 값·목적·보존기간 표시
→ 사용자 승인
→ 현재 사용자 범위로 암호화해 저장
→ 다시 읽어 값과 만료 시각 확인
```

두 번째 흐름은 별도 선호 DB와 관리 화면이 생긴 뒤에만 가능하다.

## 범위에서 제외하거나 뒤로 미룰 항목

- 감정이나 의식이 있다고 주장하는 인격화
- 사용자가 말하지 않은 건강·관계·정치 성향 자동 추론
- 파일·화면 전체를 기본값으로 클라우드 모델에 전송
- 브라우저 기록을 원격으로 보내 음악 후보를 고르는 방식
- 검증 없이 성공했다고 음성으로 답하는 범용 화면 클릭
- 기존 정책을 우회하는 사용자 제작 shell 스킬
- 시험 API를 상용·무제한 서비스로 가정한 배포

## 전체 일정 판단

- 기존 제품 경계와 실제 장시간 검증: 약 1~2주
- 작은 체감 확장 세트: 추가 2~4주
- 로컬 대화와 동의 기반 선호 기억: 추가 3~5주
- 문서·외부 서비스·SDK 중 하나: 항목별 추가 2~5주

따라서 자기소개·실제 음악 재생·상황 추천까지 안정적으로 보여 주는 다음 단계는 약 3~6주,
대화·선호 기억까지 포함한 1차 개인화 버전은 약 6~10주가 현실적이다. 모든 아이디어를 한 번에 넣는
것보다 P0 경계를 끝낸 뒤 P1을 하나씩 실제 사용자 시나리오로 검증하는 편이 SKILLA의 강점을 유지한다.

현재는 사용자 요청에 따라 조사만 수행했으며 표의 확장 기능을 구현하지 않았다.
