# SKILLA 로컬 대화·PC 명령 분리 사전 연구

상태: 조사·설계 전용, 미구현

작성일: 2026-11-18

## 문제

현재 SKILLA는 STOP과 일부 고정 명령을 제외한 입력을 NVIDIA NIM 의도 판정기로 먼저 보낸다. 향후
자기소개와 일상대화를 로컬에서 처리하더라도 이 순서를 유지하면 대화 원문이 원격으로 먼저 전송된다.
따라서 원격 호출 전에 로컬에서 입력 경로를 정해야 한다.

로컬 분리기는 실행 권한을 주는 구성요소가 아니다. PC 명령 가능성을 찾고 사용자에게 원격 전송
확인을 요청할 수 있을 뿐이며, Windows 기능 실행은 기존 정책·승인·검증 경로만 수행한다.

## 검토한 방식

| 방식 | 장점 | 한계 | 판단 |
|---|---|---|---|
| 키워드 규칙만 사용 | 빠르고 모델 불필요 | 자연스러운 한국어, 부정·가정·인용을 놓침 | STOP·고정 명령에만 사용 |
| 대화/명령 모드를 사용자가 직접 선택 | 개인정보 경계가 명확 | 매번 모드를 바꾸면 대화가 끊김 | 실패 시 안전 대체 경로 |
| 작은 분류 전용 모델 | 빠른 실행 가능 | 한국어 학습자료·배포·정확도 검증이 별도로 필요 | 장기 최적화 후보 |
| 로컬 Qwen 4B 구조화 판정 | 자유로운 한국어와 문맥 처리 가능 | 모델 준비 시간·VRAM·오판 가능성 | 초기 비교시험 후보 |
| 원격 모델로 먼저 판정 | 현재 코드 변경이 작음 | 대화 원문 비전송 목표를 충족하지 못함 | 대화 확장에는 사용하지 않음 |

권장 초기 구조는 `로컬 고정 규칙 + 로컬 4B 구조화 판정 + 전송 직전 사용자 확인`이다. 로컬 모델을
사용할 수 없으면 원격으로 자동 대체하지 않고 고정 응답과 사용자가 직접 선택하는 PC 명령 모드만
제공한다.

## 출력 규격

로컬 분리기는 다음 네 결과 중 하나만 반환한다.

| 결과 | 의미 | 다음 동작 |
|---|---|---|
| `LOCAL_FIXED` | STOP, 자기소개, 도움말처럼 고정된 로컬 기능 | 모델 호출 없이 로컬 처리 |
| `LOCAL_CONVERSATION` | 잡담·질문·이전 대화 연결 | 로컬 대화 모델과 로컬 TTS |
| `PC_COMMAND_CANDIDATE` | Windows 상태 확인·변경 요청 가능성 | 전송할 문장과 자료 종류를 표시하고 승인 대기 |
| `LOCAL_CLARIFY` | 대화인지 PC 작업인지 불명확 | 로컬에서 한 번 되묻고 원격 전송하지 않음 |

분리기 응답에는 `route`, 0~1 신뢰도, 짧은 이유 코드만 허용한다. 새로운 capability, 실행 인자,
경로 또는 shell 문장을 만들 수 없다.

## 권장 처리 흐름

```text
음성·텍스트 입력
→ 로컬 입력 검증과 STOP
→ 로컬 고정 자기소개·도움말 확인
→ 로컬 분리기
   ├─ LOCAL_CONVERSATION → 로컬 대화 모델 → 로컬 TTS
   ├─ LOCAL_CLARIFY → 로컬 확인 질문 → 다시 분리
   └─ PC_COMMAND_CANDIDATE
        → 전송 대상 문장과 자료 종류 표시
        → 사용자 승인
        → NIM 의도 판정·계획
        → 기존 정책·승인·실행·검증
```

사용자가 전송을 거절하면 입력을 폐기하거나 로컬 도움말만 제공한다. 거절한 문장을 나중에 자동으로
전송하지 않는다.

## 자연스러움과 개인정보의 균형

매 요청마다 긴 경고창을 띄우면 음성 대화가 끊긴다. 초기 안전 버전에서는 PC 명령 후보가 생겼을 때
다음처럼 짧게 확인한다.

```text
PC 작업 계획을 만들기 위해 다음 문장을 NVIDIA NIM에 보냅니다.
"다운로드 폴더의 이번 주 과제 자료를 정리해 줘"
파일 본문과 음성 원본은 보내지 않습니다. 계속할까요?
```

후속 재계획에서 파일명 등 추가 자료가 필요하면 첫 확인과 별도로 실제 자료 종류를 다시 보여 준다.
포괄적인 “모두 동의”는 기본값으로 두지 않는다. 시험용 API가 아닌 배포 계약과 관측값 최소화가
완성된 뒤에만 세션 단위 동의를 검토한다.

## 실패 시 안전 동작

- 로컬 모델 미설치·초기화 실패: 고정 기능만 유지하고 PC 명령 모드 선택 버튼 표시
- 분리 결과 JSON 오류: `LOCAL_CLARIFY`
- 신뢰도 기준 미달: `LOCAL_CLARIFY`
- 대화에서 명령을 인용·부정·가정함: 로컬 대화 유지
- PC 명령을 대화로 오판함: 실행하지 않고 대화로 답함
- 대화를 PC 명령으로 오판함: 원격 전송 전에 사용자 확인에서 차단 가능
- 확인 창 시간 초과·취소: 원격 요청 0건
- STOP: 분리 모델과 확인 창을 모두 중단하고 대기 상태 복귀

오판이 Windows 실행이나 원격 전송으로 곧바로 이어지지 않는 것이 핵심이다.

## 시험 문장 60개 구성

| 구분 | 개수 | 예시와 확인 내용 |
|---|---:|---|
| 고정 로컬 | 8 | 자기소개, 도움말, STOP |
| 일반 대화 | 12 | 인사, 취향 질문, 이전 발화 연결 |
| 명확한 PC 명령 | 16 | 시스템 정보, 파일 정리, 프로그램 실행, 음량 변경 |
| 애매한 표현 | 8 | “이거 좀 볼까”, “정리하면 좋겠네” |
| 인용·부정·가정 | 8 | “파일을 지우라는 말은 아니야”, “지운다면 어떻게 돼?” |
| 민감정보 포함 | 8 | 건강·금융·가족·비밀번호가 섞인 문장 |

합계 60개다. 음성 인식 결과와 직접 입력 결과를 각각 시험하되 같은 문장 ID로 연결한다.

## 합격 기준

- 일반 대화·민감정보 문장의 원격 요청 0건
- 사용자 승인 전 NIM 요청 0건
- 인용·부정·가정 문장의 Windows 실행 0건
- `LOCAL_CONVERSATION` 경로의 capability 호출 0건
- 명확한 PC 명령 16개 중 15개 이상이 전송 확인 단계에 도달
- 애매한 표현 8개 모두 로컬 확인 또는 대화로 처리
- 잘못된 JSON·모델 종료·시간 초과에서 원격 fallback 0건
- STOP 뒤 추가 모델 요청·TTS·Windows 실행 0건
- 준비 완료 뒤 로컬 분리 시간 중앙값 1.0초 이하
- 전체 경로 판정 근거는 원문 없이 route·reason code·지연만 기록

## 구현 전 결정할 사항

1. PC 명령 전송을 매번 확인할지, 검증된 비민감 명령만 세션 동의를 허용할지
2. 로컬 대화 모델과 분리 모델을 같은 Qwen 4B로 공유할지 작은 전용 모델을 둘지
3. 음성 확인 문구의 길이와 화면에 표시할 원문 범위
4. 민감정보가 섞인 PC 명령을 로컬에서 거절할지 민감 부분을 제거해 다시 확인할지
5. 로컬 모델을 선택 다운로드로 둘지 설치본에 포함할지

## 결론

자연스러운 대화와 현재 PC 자동화를 함께 제공하려면 로컬 분리기만으로는 부족하다. 로컬 판정 뒤에도
원격 전송 직전 사용자 확인을 두어야 사적인 대화의 오분류를 막을 수 있다. 초기에는 확인 횟수가
늘더라도 이 경계를 유지하고, 실제 오판율과 사용자 불편을 측정한 뒤 비민감 명령에 한해 단계를 줄이는
순서가 적절하다.

현재는 사용자 요청에 따라 조사만 수행했으며 라우터·UI·모델을 구현하지 않았다.
