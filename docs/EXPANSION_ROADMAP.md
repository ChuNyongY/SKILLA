# SKILLA 확장성 연구와 구현 순서

전체 후보의 현재 기반, 주제 적합도, 예상 기간과 P0~P3 우선순위는
`docs/EXPANSION_FEASIBILITY_MATRIX.md`에 정리했다.

## 1. 확장 원칙

SKILLA의 확장은 기능 이름만 등록하는 것으로 끝나지 않는다. 실제 제품에서 사용할 기능은 다음 여섯
요소를 모두 가져야 한다.

1. 기능 규격: 기능 이름, 입력값, 위험도, 상태 변경 여부
2. 입력 계약: 허용하는 값과 거부할 값을 정한 자료형 규칙
3. 실행 정책: 대상·권한·사용자 승인 조건
4. 실행기: Windows 또는 등록 프로그램을 실제로 조작하는 코드
5. 독립 검증기: 실행기의 성공 응답과 별개로 실제 상태를 다시 확인하는 코드
6. 스킬 연결: 검증된 기능만 스킬의 허용 기능 목록에 저장

현재 `build_product_capability_stack`은 실행기와 검증기의 기능 목록이 다르면 시작 단계에서 거부한다.
언어 모델에 공개되는 기능도 이 검증된 교집합으로 한정된다. 따라서 새 기능을 추가해도 기존 스킬의
권한이 자동으로 늘어나지 않는다.

## 2. 우선 확장 대상

### A. 브라우저 기록 기반 음악 재생

사용 예: `평소에 듣던 노래 틀어 줘`

권장 구성:

- `browser.history.search`: 크롬 기록의 복사본을 읽어 YouTube 방문 후보만 로컬에서 검색
- `media.candidate.rank`: 최근성·반복 횟수·재생 페이지 여부로 후보 정렬
- `media.youtube.play`: 사용자가 선택했거나 점수 차이가 충분한 영상만 재생
- `media.youtube.verify`: 열린 영상 주소와 실제 재생 상태를 별도로 확인

개인정보 경계:

- 최초 사용 시 브라우저 기록 사용 동의
- 전체 기록과 검색어는 NIM으로 전송하지 않음
- 모델에는 곡 후보의 최소 정보만 제공
- 여러 후보의 점수가 비슷하면 자동 선택하지 않고 사용자에게 확인
- 실행 기록에는 선택한 기능, 결과, 후보 선택 이유만 저장

Chromium은 방문 시각을 `visits` 테이블에, 주소·제목·방문 횟수를 `urls` 테이블에 관리한다. 실행 중인
브라우저 DB를 직접 수정하지 않고 읽기 전용 복사본에서 필요한 열만 조회해야 한다. 안정적인 재생 확인은
화면 문구 추측보다 YouTube IFrame Player API의 `onStateChange`와 `getPlayerState()`를 이용하는 전용
로컬 플레이어가 유리하다. 일반 크롬 탭을 유지하려면 Chrome 확장과 Native Messaging으로 SKILLA와
연결하는 방식이 더 안정적이다.

예상 구현 기간: 기본형 3~5일, 재생 상태 검증과 예외 처리 포함 7~10일

### B. 상황 감지형 스킬

사용 예:

- 게임 실행 감지 → 음량과 전원 설정 적용
- 수업 프로그램 실행 감지 → 강의 폴더와 메모장 열기
- 지정 시간 도달 → 승인 후 반복 정리 실행

프로세스 시작, 활성 창 변경, 예약 시각을 `상황 신호`로 다룬다. 상황 신호는 스킬을 바로 실행할 권한이
아니다. 일치한 스킬을 제안하거나, 사용자가 미리 자동 실행을 허용한 낮은 위험 작업만 시작한다.

예상 구현 기간: 앱 실행 감지 3~5일, 시간 예약과 자동 실행 정책 포함 7~12일

### C. 매개변수 스킬

현재 폴더, 이번 주 파일, 음량 값처럼 매번 달라지는 값을 스킬 절차와 분리한다. 스킬에는 값 자체가 아니라
`입력값을 어디서 읽는지`, `허용 범위`, `확인 방법`을 저장한다.

사용 예:

- `과제 자료 정리` + 현재 다운로드 폴더
- `PDF 열기` + 사용자가 말한 문서명
- `집중 모드` + 사용자가 지정한 음량

예상 구현 기간: 5~8일

### D. 실패 복구 절차

오류 코드마다 검증된 복구 방법을 등록한다.

- 마이크 장치 사라짐 → 기본 입력 장치로 시작 전 1회 전환
- 입력 스트림 정지 → 정지 감지 후 제한된 캡처 재시작
- 파일명 변경 → 허용 폴더에서 동일 해시 또는 사용자 지정 조건으로 재탐색
- 창 위치 변경 → 좌표 대신 UI Automation 요소를 다시 검색
- 브라우저 자동 재생 차단 → 재생 버튼을 사용자에게 표시하고 클릭 후 상태 재검증

복구가 외부 효과를 중복시킬 가능성이 있으면 자동 재시도하지 않는다.

예상 구현 기간: 공통 복구 규격 3~5일, 기능별 복구 규칙은 기능당 1~3일

### E. 기능 묶음과 배포 검사

파일, 브라우저, 미디어, 학습, 게임 준비처럼 관련 기능을 묶되 각 묶음은 다음 검사를 통과해야 한다.

- 실행기와 검증기의 기능 ID 일치
- 모든 기능에 입력 계약 존재
- 위험도와 승인 규칙 존재
- 실패·중단·시간 초과 시험 존재
- 깨끗한 Windows 사용자 계정에서 설치 시험
- 장치 번호와 앱 경로가 달라도 진단 결과가 명확하게 표시

예상 구현 기간: 공통 검사 도구 3~5일, 깨끗한 PC 배포 검증 2~4일

## 3. 안정화 단계

### 현재 반영

- 지정 마이크가 시작 전에 사라지면 Windows 기본 입력 장치로 한 번 전환
- 입력 프레임이 일정 시간 오지 않으면 `AUDIO_INPUT_STALLED`로 감지
- 스트림 시작·중지·닫기 실패를 제품 외부로 노출하지 않고 정해진 오류 코드로 처리
- 입력 정지 오류는 기존 제한된 캡처 재시작 흐름으로 전달
- 시작 진단에서 지정 마이크 또는 기본 마이크의 16 kHz mono int16 지원 확인
- Chrome 실행 중 잠긴 History DB를 원본 변경 없이 임시 스냅샷으로 읽는 경로
- 최근 30일의 최근 항목 또는 방문 횟수가 많은 YouTube 항목 선택
- 영상 주소·제목을 NIM과 UI 결과에 노출하지 않는 `media.youtube.play.recent` 기능
- 등록 Chrome 새 창과 선택 해시를 다시 확인하는 독립 검증기
- 한국어 검색어를 UTF-8로 변환해 등록 Chrome 또는 Edge의 Google 검색 창을 여는 기능
- 검색어 원문 대신 SHA-256 결합값만 실행 결과에 남기는 `browser.search.web` 기능
- 정확한 브라우저·Google 허용 목록·새 창 상태를 다시 확인하는 독립 검증기
- 등록된 프로그램 ID와 승인된 스킬 버전을 연결하는 로컬 상황 감지 규격
- 검증된 전경 프로그램 전환 시 한 번만 제안하고 자동 실행하지 않는 스킬 제안 엔진
- 스킬이 폐기·개정되거나 연결 규칙이 바뀌면 기존 제안을 거부하는 재검증 경계
- 제품 호스트와 함께 시작·종료되는 Windows 전경 프로그램 감시기
- 한 번에 제안 하나만 보관하고 정확한 제안 ID로 승인·닫기를 처리하는 보류 제안함
- HUD에서 감지한 프로그램과 스킬 이름을 표시하고 사용자 승인 뒤 기존 안전 실행 흐름으로 전달
- 감시 오류·이벤트 순서 오류·이벤트 큐 초과 시 자동 실행 없이 중단하는 실패 차단 구조
- 요일·시각·정확한 스킬 버전을 로컬 DB에 저장하는 예약 스킬 관리 화면
- 같은 현지 시각에는 한 번만 제안하고 재시작 뒤에도 중복 제안을 막는 예약 실행 기록
- 예약 시각이 되면 HUD에서 실행 여부를 다시 묻고 기존 안전 실행·검증 흐름으로 전달
- 예약된 스킬이 폐기·개정됐거나 규칙이 중지되면 실행하지 않는 재검증 경계
- 상황·예약 제안에서 스킬에 선언된 동적 입력만 사용자에게 다시 받는 실행 입력 창
- 입력 이름의 누락·추가, 빈 값, 제어문자, 길이 초과를 실행 전에 차단하는 매개변수 결합 규격
- 입력 창을 취소하면 제안을 소비하거나 작업을 시작하지 않는 취소 경계
- 입력을 받은 뒤에도 스킬 ID·버전을 다시 확인하고 기존 정책·승인·검증 흐름으로 전달
- 상황·예약 제안에서 승인한 스킬 ID·버전을 내부 신뢰 문맥에 고정해 자연어 재검색으로 다른 스킬이
  선택되는 경로를 차단
- 내부 스킬 고정값과 현재 전경 프로그램 문맥은 충돌 여부를 검사해 병합하고, 잘못된 ID·버전·폐기된
  스킬은 언어 모델 호출 전에 거부
- NIM 계획 요청의 명시적 일시 HTTP 응답(429·502·503·504)만 최대 2회 지수 지연 재시도
- 서버 `Retry-After`는 최대 5초로 제한하고, 영구 오류와 결과가 모호한 연결 오류는 자동 재시도하지
  않아 작업 중복과 무제한 대기를 차단
- 스킬·실행기록·상황규칙·예약규칙 SQLite DB를 쓰기 전에 `quick_check`로 무결성 확인
- 네 상태 DB에 WAL 저널·FULL 동기화·제한된 잠금 대기를 공통 적용하고, 손상된 DB는 원본을
  덮어쓰지 않은 채 저장소별 안정 오류로 시작 중단
- 사용자가 지정한 새 폴더에 스킬·실행기록·상황규칙·예약규칙 DB의 일관된 SQLite 스냅샷 생성
- 백업 목록·파일 크기·SHA-256·SQLite 무결성을 함께 검사하고, 파일 누락·추가·변조 시 복원 차단
- 정확한 확인 문구가 있어야만 복원하며, 복원 직전 상태를 별도 롤백 폴더에 보관
- 복원 도중 일부 파일 교체가 실패하면 이미 교체한 DB도 직전 상태로 되돌리는 임시 환경 시험 통과
- 네 상태 DB 각각에서 커밋 뒤 미완료 쓰기 중 별도 프로세스를 강제 종료하는 WAL 복구 시험 통과
- 강제 종료 뒤 커밋된 기록만 남고 미완료 기록은 제외되며, 네 DB 동시 백업에도 같은 결과가
  보존되는지 확인
- 정상적인 장시간 캡처 구간 종료는 실패 재시도 횟수에서 제외하고, 정상 구간이 확인되면 이전의
  연속 캡처 실패 횟수를 초기화하도록 호스트 수명 주기 수정
- 실제 캡처 실패만 제한된 재시도 횟수에 포함하며 정상 구간 반복과 실패-정상-실패 복구 시험 통과
- 80ms 음성 프레임 360,000개를 연속 처리하는 8시간 상당 가속 대기 시험에서 작업 오실행 없이
  프레임 한도 도달과 캡처 자원 정리를 확인
- 지정 마이크가 실행 중 멈춘 뒤 캡처를 재시작할 때 해당 장치가 사라진 상황을 모의하고, Windows
  기본 입력 장치로 전환해 프레임 수신을 재개하며 이전 스트림을 정리하는 시험 통과
- 로컬 중단 신호를 의도 판정기·스킬 계획기·NIM 전송 계층까지 동일하게 전달
- NIM의 5초 재시도 대기 중 중단하면 두 번째 요청 없이 즉시 계획을 취소하고 런타임이 대기 상태로
  복귀하는 시험 통과
- Windows 강제 종료 직후 드물게 발생하는 SQLite `BUSY`·`LOCKED`·`IOERR`만 짧게 최대 2회
  재검사하고, 실제 손상이나 반복 오류는 기존처럼 시작을 차단하도록 보완
- 네 DB 강제 종료·WAL 복구 시험을 10회 연속 반복해 총 50개 복구 사례 통과

현재 검증 범위는 선택한 YouTube 페이지가 등록 Chrome 새 창에서 열렸는지까지다. 브라우저 자동 재생
정책에 따라 실제 소리가 바로 재생되지 않을 수 있으므로, 재생 상태까지 확정하려면 Chrome Native
Messaging 또는 전용 YouTube IFrame 플레이어 연결이 다음 단계다.

여러 단계 재계획의 관측값은 2026-11-18 source부터 capability별 허용 projection을 거친다. 시스템
이름·파일명·경로·PID·HWND·hash는 후속 NIM 문맥에서 제거하고, 파일 목록은 작업용 무작위 handle과
파일 종류·안전한 확장자만 전달한다. `file.move`와 `file.delete.trash` 실행 직전에 handle을 로컬
경로로 복원하고 최초 identity를 다시 검사한다. 최종 planner JSON 직전에도 projected schema와
경로·UNC·URL·이메일 패턴을 재검사한다. 기존 0.2.11 설치본에는 이 변경이 없다.

5. 깨끗한 Windows 계정과 저사양 PC 설치 시험

## 4. 대화형 동반자 확장 조사(미구현)

사용 예: `자기소개해 봐`, `오늘 기분이 어때?`, `내가 좋아하는 음악 기억해 둬`

현재 제품은 질문과 잡담을 실행 명령과 구분해 `RESPOND` 경로로 보내는 의도 판정 규격을 갖고 있다.
그러나 `RESPOND` 경로에 자유 대화 응답 생성기와 음성 출력이 연결되어 있지 않다. 현재 SQLite 기억은
검증된 작업과 사용자가 명시적으로 저장하라고 한 낮은·중간 민감도 정보용이며, 대화에서 자동으로
개인 성향을 추측해 저장하는 구조가 아니다. 따라서 자기소개 한 문장만 고정 출력하는 기능과 사용자의
선호를 기억하며 관계를 이어가는 기능은 서로 다른 개발 단계로 구분해야 한다.

권장 단계:

1. 정체성 카드: 이름, 역할, 할 수 있는 일과 할 수 없는 일을 코드에 고정해 자기소개 생성
2. 대화 응답기: 질문·잡담은 로컬 대화 모델로 보내고 실행 기능 호출을 차단하는 별도 응답 규격
3. 대화 음성 출력: 500자 이하 검증 문장만 현재 Supertonic TTS로 전달
4. 명시적 사용자 기억: `기억해 둬` 요청과 저장 전 확인을 거친 선호만 로컬 DB에 저장
5. 기억 관리 화면: 저장된 선호 보기·수정·삭제·전체 초기화
6. 관계 표현 규칙: 과도한 의인화나 사실과 다른 감정 표현 없이 일관된 말투와 이전 대화 연결
7. 평가: 자기소개 정확성, 명령 오실행 0건, 기억 재현 정확도, 삭제 반영, 응답 지연, 사용자 만족도

수정 예상 기간(개발자 1명, 현재 코드 기준):

- 고정 자기소개와 텍스트 응답: 0.5~1일
- 자기소개 TTS와 STOP 처리: 1~2일
- 로컬 Qwen 4B 격리 성능시험: 2.5~4일
- 로컬 `RESPOND` 연결과 최근 문맥: 4~7일
- 동의 기반 선호 기억·조회·수정·삭제 UI: 1~2주
- 30개 대화 시나리오와 장시간 음성 검증: 4~7일
- 자연스러운 유대감 형성 1차 완성: 총 3~5주
- 다른 사용자에게 배포할 수준의 개인정보·설치·업데이트 검증: 총 5~8주

초기 2~3주 추정은 원격 NIM에 자유 대화를 연결하는 전제였다. NVIDIA 시험 API의 개인정보 제한과
현재 PC에서 가능한 로컬 모델을 확인한 뒤, 개인 대화는 로컬 Qwen 모델로 분리하는 일정으로 수정했다.
사용자의 기분·건강·관계 정보를 자동 추론해 저장하지 않고, 저장 항목과 보존 기간을 사용자가 직접
확인할 수 있게 하는 것이 전제다.

### 2026-11-18 공식 자료와 현재 코드 대조 결과(조사만 수행)

- NVIDIA NIM의 Chat Completions 규격은 여러 `messages`를 받는 대화 형식과 스트리밍 응답을
  지원한다. 따라서 새 대화 모델을 학습하지 않고도 현재 GLM 계열 모델에 제한된 최근 대화 문맥을
  전달할 수 있다.
- 현재 `NimChatTransport`는 매 요청에 시스템 문장과 사용자 문장 한 개만 보내고 `stream=false`를
  사용한다. 현재 구조 그대로는 이전 대화를 이어서 기억하거나 말이 생성되는 즉시 읽어 주지 않는다.
- 현재 `RESPOND` 판정은 질문·잡담을 실행 계획과 분리하는 데까지만 구현되어 있다. 이 경로는
  실행 capability를 만들지 않으므로 대화 응답기를 붙일 위치로 적합하지만, 응답 생성·표시·TTS 연결은
  아직 없다.
- 현재 Supertonic 3은 로컬 CPU ONNX 방식이라 대화 문장을 외부 TTS 서비스에 보내지 않고 한국어로
  읽을 수 있다. 다만 공식 오픈소스 저장소는 2026년 9월 보관 상태로 전환되어 이후 수정·보안 지원이
  제공되지 않는다. 당장 제거할 이유는 없지만 배포 장기 유지보수에서는 대체 TTS 시험이 필요하다.
- 현재 SQLite 기억은 명시적인 제한형 저장소로 사용할 수 있지만, 대화 전체를 자동 저장하는 것은
  기존 개인정보 경계와 맞지 않는다. 선호는 `기억해 둬` 같은 직접 요청과 저장 전 확인을 통과한 항목만
  별도 종류로 저장하고, 보기·삭제·만료 기능을 같은 단계에서 제공해야 한다.
- 가장 작은 기능인 고정 자기소개는 모델 호출 없이 만들 수 있다. 반면 사용자와의 유대감은
  대화 문맥, 동의 기반 선호 기억, 삭제 반영, 일관된 말투, 명령 오실행 방지를 함께 검증해야 하므로
  단순 자기소개와 같은 기능으로 계산하면 안 된다.

조사 결론은 현재 기능을 확장하지 않은 상태에서 작성했다. 실제 구현 전 확인할 핵심 선택은
`최근 대화의 보존 범위`, `기억 항목의 종류와 만료 기간`, `음성 응답 중 STOP 처리`,
`Supertonic 장기 유지 여부` 네 가지다.

원격 의도 판정 전에 대화와 PC 명령을 나누는 네 가지 route, 전송 직전 확인, 60개 분리 시험 기준은
`docs/LOCAL_INPUT_ROUTING_STUDY.md`에 별도로 정리했다.

현재 단계의 결론은 Supertonic을 즉시 교체하는 것이 아니라 `현행 Supertonic`, `MOSS-TTS-Nano
ONNX`, `MeloTTS Korean` 세 후보를 같은 한국어 문장으로 비교하는 것이다. 비교 문장은 자기소개,
숫자·날짜·파일명, 한영 혼합어, 긴 문장, 명령 결과, 감탄·질문을 포함한다. 각 후보에서 첫 음성까지의
시간, 전체 생성 시간, 최대 메모리, 문장 누락·반복, 5점 청취평가를 기록해야 한다. 음성 복제 기능은
이번 비교에서 제외해야 모델 간 조건과 동의 범위가 달라지지 않는다.

### 현재 GLM-5.3-Flash 대화 사용 가능성 조사(미구현)

- 제품 설정은 NVIDIA의 원격 `integrate.api.nvidia.com`에서
  `z-ai/glm-5.3-flash`를 호출한다. 스킬 저장·실행, STT와 TTS는 로컬이지만 현재 LLM 추론까지
  사용자 PC에서 실행하는 완전 로컬 구조는 아니다.
- 공식 모델 카드는 채팅, 도구 호출, 최대 1,048,576토큰 문맥을 지원한다고 설명한다. 기능만 보면
  자기소개와 짧은 일상대화가 가능하지만, 시험 API 개인정보 조건 때문에 개인 대화의 기본 경로로
  사용하지 않는다.
- NVIDIA Build는 무료 시험용 endpoint를 제공하지만 모델 다운로드는 제공하지 않는다. 제휴
  serverless 가격은 공급자별로 100만 입력 토큰당 미화 0.08~0.15달러, 출력 토큰당
  0.25~0.50달러로 표시된다. 무료 endpoint를 장기 배포의 무제한 무료 서비스로 가정하면 안 된다.
- 자체 NIM 배포는 205~645GB 모델 파일과 다수의 H200·B200·GB200급 GPU를 요구한다. 현재 개발
  PC의 단일 소비자용 GPU에 같은 모델을 올리는 방식은 현실적인 대안이 아니다.
- 현재 전송 계층은 `reasoning_effort=low`, `clear_thinking=true`, `max_tokens=3000`을 사용한다.
  공식 안내의 채팅 설정과 맞지만, 매 호출에서 이전 대화를 보내지 않으므로 실제 다회 대화 기억은 없다.
- 개인 대화의 최근 4~8개 발화는 로컬 모델 문맥에만 두고, 사용자가 저장을 승인한 선호만 로컬
  SQLite에 남기는 편이 개인정보와 응답 지연을 함께 줄인다.
- 대화 기능을 만들 때 원격 LLM 연결 실패는 PC 작업의 계획 생성에만 영향을 줘야 한다. 고정
  자기소개, 로컬 상태 안내와 로컬 자유 대화는 계속 사용할 수 있도록 분리한다.

### NVIDIA 시험 API 개인정보 경계 조사(미구현)

- 현재 의도 판정기는 로컬 중단 명령과 일부 시스템 정보 명령을 제외한 발화 원문을 최대 2,000자까지
  NVIDIA 원격 API에 보낸다. 명령으로 판정되면 계획 생성 단계에서도 같은 요청 내용이 다시 원격
  API 입력에 포함될 수 있다. 음성 원본 파일이 아니라 STT로 만든 문자열이 전송되는 구조다.
- NVIDIA API Trial 약관은 별도 허용이 없는 한 기밀·민감정보와 개인 데이터를 입력하지 말라고
  명시한다. 일반 세션 종료 후 입력·출력을 저장하거나 사용하지 않는다는 조항이 있지만, 보안·사기·
  남용 방지를 위한 기록 가능성과 서비스별 별도 공개 예외가 있다. 이를 `어떤 개인정보든 자유롭게
  보내도 된다`는 의미로 해석하면 안 된다.
- 무료 API는 시험·평가·개발용이다. 다른 사용자에게 배포하는 제품 단계에서는 같은 시험 key를
  기본 서비스처럼 사용하지 말고, 적용되는 상용 공급자 계약과 개인정보 조건을 다시 확인해야 한다.
- 따라서 현재 시험 API 위에 `내 건강 상태 기억해`, `가족 이야기 기억해`처럼 개인적인 대화를
  연결하는 것은 적절하지 않다. 사용자가 명시적으로 저장한 로컬 선호와 원격 모델에 보내는 문맥도
  서로 분리해야 한다.
- 향후 화면에는 `명령 문자열이 NVIDIA API로 전송될 수 있음`, `민감정보 입력 금지`, `음성 원본은
  전송하지 않음`을 실행 전에 알리는 표시가 필요하다.
- 대화 확장 전 필수 조건은 원격 전송 표시, 민감정보 차단, 최근 문맥 상한, 전송하지 않는 로컬
  자기소개 경로, 기억 보기·삭제 기능이다. 이 조건을 충족하기 전에는 유대감 기능을 시험 API에
  연결하지 않는다.

### 현재 PC에서 가능한 로컬 대화 모델 조사(미설치·미구현)

읽기 전용 장치 확인 결과는 Ryzen 5 9500F 6코어/12스레드, RAM 15.4GB, RTX 5060 Ti 8,151MiB다.
이 사양에서는 GLM-5.3-Flash 자체 구동은 불가능하지만 4B급 모델의 4비트 양자화본은 비교 시험이
가능한 범위다.

- 1차 후보는 `Qwen3.5-4B`다. 공식 weight는 Apache-2.0, 201개 언어·방언, 대화와 도구 호출을 지원한다.
  다만 기본 262K 문맥은 8GB VRAM에 맞지 않으므로 실제 비교에서는 텍스트 전용, 비사고 모드,
  4비트 GGUF, 8K 안팎의 제한된 문맥부터 시작해야 한다.
- 보수적인 비교 후보는 `Qwen3-4B-Instruct-2507`이다. Qwen 공식 문서는 100개 이상의 언어와
  다회 대화·도구 사용을 설명한다. 두 후보 모두 실제 Q4 GGUF의 출처·revision·hash와 원본 라이선스를
  성능시험 전에 고정해야 한다.
- 실행기는 `llama.cpp`의 Windows CUDA 빌드와 localhost 전용 OpenAI 호환 server가 적합하다.
  모델 일부를 GPU에 올리고 부족한 부분을 CPU·RAM으로 나눌 수 있으며, 외부 주소에 bind하지
  않으면 대화 내용을 PC 밖으로 보내지 않는다.
- 로컬 모델은 우선 자유 대화와 자기소개에만 사용하고 Windows 실행 계획 권한을 주지 않는다.
  4B 모델의 자연스러운 대화 가능성과 신뢰할 수 있는 PC 실행 계획 능력은 같은 기준이 아니다.
- 개인정보를 지키려면 현재 원격 의도 판정 전에 로컬 규칙 또는 로컬 모델이 `대화`와 `실행 명령`을
  먼저 분리해야 한다. 대화는 로컬 모델에서 끝내고, 사용자가 명확히 요청한 PC 명령만 원격 NIM
  계획 경로로 보낸다는 이중 경계가 필요하다.

실제 비교를 허용받으면 30개 한국어 문장으로 첫 토큰 지연, 생성 속도, VRAM/RAM 최고값,
자기소개 사실 일치, 이전 4턴 기억, 민감정보 비전송, 명령 오실행 0건을 측정한다. 현재는 모델·실행기
다운로드와 성능 시험을 수행하지 않았다.

로컬 사용자 선호 저장 구조의 현재 기능과 부족한 관리 경계는
`docs/USER_PREFERENCE_MEMORY_STUDY.md`에 별도로 정리했다. 기존 semantic memory에 선호 값을
바로 섞지 않고, 허용 key·동의 시각·만료·목록·삭제를 갖춘 별도 저장소를 먼저 검증하는 방향이다.

자기소개부터 로컬 대화·선호 기억·배포 검증까지의 단계와 수정된 예상 기간은
`docs/COMPANION_READINESS.md`에 통합했다.

상세 비교 조건과 합격 기준은 `docs/LOCAL_CONVERSATION_STUDY.md`에 고정했다.

## 5. 현실적인 완성 일정

- 3~5일: 장시간 음성 시험, 연결 오류 처리, 대표 스킬 5개 회귀시험
- 1~2주: 음악 재생 기본형, 상황 감지, 매개변수 스킬 1차
- 3~4주: 음악 재생 검증, 앱별 복구, 깨끗한 PC 설치 시험
- 5~8주: 다른 사용자가 설치해도 사용할 수 있는 배포·업데이트·진단 체계
