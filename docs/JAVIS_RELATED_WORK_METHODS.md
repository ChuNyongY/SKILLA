# JAVIS에 반영한 스킬 관련 논문의 방법론

## 1. 문서 목적

이 문서는 JAVIS의 스킬 생성·재사용·개정 구조를 설명할 때 인용한 연구가 어떤 방법을 사용했고, 그 방법을 JAVIS에 어떻게 반영했는지 정리한다. 논문의 코드를 그대로 복사한 경우와 설계 원리만 참고한 경우를 구분하는 것이 목적이다.

JAVIS는 ReAct, Toolformer, Reflexion, Voyager를 하나로 합친 구현이 아니다. 네 연구에서 필요한 원리를 선택하고 Windows 반복 작업에 맞게 제한하였다. PC 작업 평가 방법은 UFO, OSWorld와 AgentBench를 참고하였다. 대부분의 경우 논문이 제안한 학습 절차나 실행 코드를 그대로 사용하지 않고, 스킬 계약과 실행 하네스의 설계 근거로 사용했다.

## 2. 반영 범위 요약

| 연구 | 원 논문의 핵심 방법 | JAVIS에 반영한 부분 | 그대로 사용하지 않은 부분 |
|---|---|---|---|
| ReAct | 추론과 행동을 번갈아 수행하고 환경 관찰을 다음 판단에 반영 | 계획, 기능 실행, 결과 관찰의 반복 구조 | 자유 형식 사고 과정 저장과 공개 |
| Toolformer | API 호출 후보를 만들고 실행 결과가 언어 모델 손실을 줄이는 호출만 남겨 재학습 | 기능 이름, 인자와 결과를 명시적으로 연결하는 도구 사용 구조 | 자기지도 학습, 데이터 생성, 모델 미세조정 |
| Reflexion | 실행 평가 뒤 자연어 반성문을 장기 기억에 넣어 다음 시도에 제공 | 실패 코드와 실행 근거를 개정 초안 입력으로 사용 | 모델의 자유 반성문만으로 스킬 자동 변경 |
| Voyager | 실행 코드 스킬 저장소, 관련 스킬 검색, 환경 피드백 기반 반복 개선 | 스킬 저장소, 검색, 성공·실패 기록을 이용한 새 버전 생성 | 실행 코드 저장, 자동 교육과정, 무인 승인 |
| UFO | Windows에서 앱 선택과 앱 내부 조작을 분리한 이중 에이전트 | 앱 선택 정보와 앱 내부 실행 단계를 구분하는 설계 참고 | HostAgent와 AppAgent의 다중 모델 구조 |
| OSWorld | 초기 상태 설정과 작업별 실행 기반 판정 | fixture 복원, 동일 초기 상태 해시, 독립 완료 판정 | 369개 범용 작업과 가상 환경 전체 |
| AgentBench | 여러 상호작용 환경에서 에이전트의 성공과 실패 유형을 비교 | 최종 답변보다 실제 작업 성공률과 실패 원인 측정 | 8개 환경과 29개 모델의 대규모 비교 |

## 3. ReAct의 방법과 JAVIS 적용

### 3.1 원 논문의 방법

ReAct는 Reasoning and Acting의 줄임말이다. 연구진은 언어 모델이 추론 문장과 환경 행동을 한 번에 끝내지 않고, 생각, 행동, 관찰의 순서로 반복하게 하였다. 행동 결과가 관찰로 돌아오면 모델은 그 결과를 이용해 계획을 수정한다. 논문은 질문 답변과 사실 검증에서 Wikipedia API를 사용했고, 상호작용 환경에서는 ALFWorld와 WebShop을 사용했다. 일부 과제에서는 한두 개의 예시만 프롬프트에 넣어 수행하였다.

방법의 핵심은 모델이 처음 만든 계획을 끝까지 고정하지 않는 데 있다. 외부 환경에서 얻은 결과를 다음 행동의 입력으로 사용한다. 이 구조는 파일이 없거나 예상한 창이 열리지 않은 경우 다시 관찰해야 하는 PC 작업과 연결된다.

### 3.2 JAVIS에 반영한 방법

JAVIS는 사용자 요청을 계획으로 바꾸고, 기능을 한 단계씩 실행한 뒤 실제 Windows 상태를 다시 관찰한다. 관찰 결과가 목표와 다르면 다음 단계로 넘어가지 않고 실패 또는 재계획 경로로 보낸다. 이 흐름은 ReAct의 행동·관찰 반복을 실행 하네스에 옮긴 것이다.

JAVIS는 모델의 자유 형식 사고 과정을 감사 로그에 저장하지 않는다. 계획은 기능 이름과 인자가 정해진 형식으로만 전달한다. 결과 관찰도 파일 존재, 해시, 프로세스와 창 같은 운영체제 증거로 제한한다. ReAct의 반복 구조는 사용하지만 내부 추론 문장을 시스템 기록의 근거로 사용하지 않는다.

## 4. Toolformer의 방법과 JAVIS 적용

### 4.1 원 논문의 방법

Toolformer는 언어 모델이 어떤 API를 언제 호출하고 어떤 인자를 넘길지 학습하는 자기지도 방법을 제안하였다. 먼저 소수의 API 사용 예시를 프롬프트로 제공하여 기존 텍스트의 여러 위치에 API 호출 후보를 만든다. 다음으로 후보 호출을 실제 실행한다. API 호출과 결과를 제공했을 때 이후 토큰의 예측 손실이 충분히 줄어든 사례만 남긴다. 마지막으로 남은 호출을 원문에 삽입한 자료로 모델을 미세조정한다.

논문은 질의응답, Wikipedia 검색, 계산기, 달력과 기계 번역 API를 사용했다. 추론 시점에는 모델이 API 호출을 출력하면 생성을 잠시 멈추고 실제 API 결과를 삽입한 뒤 생성을 계속한다. 이 방법은 도구 사용을 프롬프트 규칙으로만 지정하지 않고 모델 학습 자료에 포함한다.

### 4.2 JAVIS에 반영한 방법

JAVIS는 도구 호출을 기능 이름, 입력 인자와 반환 결과가 있는 구조로 다룬다. 계획기는 등록된 Windows 기능 중 필요한 기능을 고르고, 실행기는 결과를 다음 단계에 제공한다. 이 구조는 Toolformer가 API 이름·인자·결과를 언어 모델 문맥에 명시적으로 연결한 방법을 참고했다.

JAVIS는 Toolformer의 자기지도 자료 생성이나 모델 미세조정을 수행하지 않는다. NIM에서 제공하는 기존 모델을 그대로 사용하며, 기능 허용 여부는 모델이 학습한 확률이 아니라 기능 등록부와 정책 모듈이 결정한다. 따라서 Toolformer는 도구 호출을 구조화해야 하는 이유를 설명하는 관련 연구이고, JAVIS의 스킬 학습 알고리즘 자체는 아니다.

## 5. Reflexion의 방법과 JAVIS 적용

### 5.1 원 논문의 방법

Reflexion은 모델 가중치를 갱신하지 않고 언어 피드백을 다음 시도에 사용하는 방법이다. 기본 구조는 행동을 만드는 Actor, 결과를 평가하는 Evaluator, 실패 원인을 자연어로 정리하는 Self-Reflection 모듈로 이루어진다. 한 번의 실행 궤적은 단기 기억으로 사용하고, 반성문은 장기 기억 버퍼에 보관한다. 다음 시도에서 Actor는 이전 반성문을 함께 읽는다.

논문은 순차 의사결정, 코드 작성과 언어 추론 과제에서 이 구조를 평가했다. 피드백은 숫자 보상 또는 자유 형식 문장일 수 있다. 연구진은 최근 실행 궤적만 제공한 조건과 반성문까지 제공한 조건을 비교하여 반성 단계의 추가 효과를 분석했다.

### 5.2 JAVIS에 반영한 방법

JAVIS는 실행 결과를 성공 여부, 실패 코드, 실행 시간, 호출 수, 토큰 수와 독립 검증 근거로 저장한다. 같은 스킬에서 반복 실패가 나타나면 이 자료를 개정 스킬 초안을 만드는 입력으로 사용한다. 모델을 다시 학습하지 않고 실행 경험을 다음 버전에 반영한다는 점은 Reflexion과 같다.

두 시스템의 개정 권한은 다르다. JAVIS는 모델이 쓴 반성문만으로 기존 스킬을 바꾸지 않는다. 반복 실패 코드와 최소 관측 수를 먼저 확인하고, 새 절차는 DRAFT 상태로 저장한다. 사용자가 승인한 뒤에만 VERIFIED가 된다. 결과 평가도 언어 모델의 자기평가가 아니라 별도 검증기가 확인한 Windows 상태를 사용한다.

## 6. Voyager의 방법과 JAVIS 적용

### 6.1 원 논문의 방법

Voyager는 Minecraft에서 장기간 학습하는 에이전트다. 방법은 자동 교육과정, 실행 코드 스킬 저장소, 반복 프롬프트 개선의 세 부분으로 구성된다. 자동 교육과정은 현재 상태와 진행 기록을 바탕으로 다음 목표를 만든다. 성공한 행동 프로그램은 설명의 임베딩을 키로, 실행 코드를 값으로 하는 스킬 저장소에 넣는다. 새 작업에서는 관련 스킬 다섯 개를 검색해 프롬프트에 제공한다.

생성한 프로그램을 실행하면 환경 진행 상태, 코드 오류와 자기검증 결과를 얻는다. Voyager는 이 정보를 다음 프롬프트에 넣어 코드를 고치고, 자기검증이 성공할 때까지 반복한다. 성공한 프로그램만 스킬 저장소에 추가한다. 모델 가중치는 바꾸지 않는다.

### 6.2 JAVIS에 반영한 방법

JAVIS의 중심 구조는 Voyager의 스킬 저장·검색·재사용 개념과 가장 가깝다. 성공한 반복 작업에서 작업 설명, 호출 표현, 절차, 동적 입력, 판단 규칙, 검증 규칙과 허용 기능을 추출한다. 새 요청에서는 VERIFIED 스킬을 검색하고, 정확한 스킬 ID와 버전을 실행 기록에 남긴다. 실패 기록은 기존 버전을 덮어쓰지 않고 다음 DRAFT 버전을 만드는 근거로 사용한다.

JAVIS는 실행 코드를 스킬로 저장하지 않는다. 스킬에 PowerShell이나 Python을 넣을 수 없으며 등록된 기능의 조합만 허용한다. 또한 자동 교육과정으로 임의의 새 작업을 만들지 않는다. 사용자가 요청한 작업만 실행하고 새 스킬과 개정 스킬은 사람의 승인을 거친다. 이 차이는 게임 환경의 무인 탐색 방법을 개인 PC에 그대로 적용했을 때 생길 수 있는 권한 확대를 제한한다.

## 7. PC 에이전트 평가 연구의 적용

### 7.1 UFO

UFO는 Windows 작업을 HostAgent와 AppAgent로 나눈다. HostAgent는 전체 요청을 보고 사용할 응용 프로그램과 전체 계획을 정한다. AppAgent는 선택한 앱의 화면과 컨트롤 정보를 보고 구체적인 UI 동작을 반복한다. 여러 앱이 필요한 경우 AppAgent가 현재 앱의 작업을 마친 뒤 HostAgent가 다음 앱을 고른다.

JAVIS는 이중 에이전트 구조를 그대로 구현하지 않았다. 대신 요청 분석 단계에서 대상 앱과 필요한 기능을 정하고, 앱별 실행 어댑터가 실제 동작을 맡는다. 화면 조작이 필요한 경우에도 등록된 앱, 프로세스와 창 범위를 먼저 고정한다. UFO는 Windows 앱 선택과 앱 내부 행동을 분리하는 설계 근거로 사용했다.

### 7.2 OSWorld

OSWorld는 실제 운영체제에서 작업을 재현하기 위해 작업별 초기 상태 설정과 실행 기반 평가 스크립트를 함께 제공한다. 공개 논문은 369개 작업을 구성하고 파일 입출력, 웹·데스크톱 앱과 여러 앱을 오가는 작업을 포함했다. 평가자는 에이전트의 최종 문장을 채점하지 않고 작업 후 환경 상태를 검사한다.

JAVIS 실험은 이 원리를 작은 Windows 작업 집합에 적용했다. 각 조건 전에 같은 fixture를 새 임시 폴더에 복원하고 초기 상태 SHA-256을 비교한다. 파일 이동은 목적 폴더와 파일 내용을, 앱 실행은 새 프로세스와 대상 창을 검사한다. JAVIS가 OSWorld의 작업이나 코드를 가져온 것은 아니며, 초기 상태와 완료 판정을 분리하는 평가 방법을 참고했다.

### 7.3 AgentBench

AgentBench는 8개 상호작용 환경에서 29개 언어 모델을 비교하고 성공률과 실패 원인을 분석하였다. 이 연구는 에이전트 평가에서 장기 추론, 의사결정과 지시 이행을 실제 환경 행동으로 측정해야 한다는 근거를 제공한다.

JAVIS는 여러 모델을 비교하지 않았다. 같은 모델과 같은 기능을 고정하고 스킬 제공 조건만 SK0~SK3으로 바꾸었다. AgentBench의 대규모 벤치마크를 재현한 것이 아니라, 답변 품질과 실제 작업 성공을 구분하고 실패 유형을 기록하는 평가 원칙을 사용했다.

## 8. JAVIS 연구 방법으로의 결합

### 8.1 구현 방법

관련 연구에서 가져온 방법은 다음 실행 순서로 결합하였다.

1. 사용자 요청을 분석하고 VERIFIED 스킬을 검색한다.
2. 스킬의 절차와 허용 기능을 사용해 형식화된 계획을 만든다.
3. 정책과 승인을 통과한 기능만 실행한다.
4. 실행기와 분리된 검증기가 실제 Windows 상태를 확인한다.
5. 성공·실패, 비용과 근거를 사용한 스킬 버전에 연결한다.
6. 반복 실패 기준을 충족하면 개정 DRAFT를 만들고 사람 검토를 기다린다.

ReAct는 2단계부터 4단계까지의 행동·관찰 반복에, Toolformer는 2단계의 구조화된 기능 호출에 해당한다. Reflexion은 5단계와 6단계의 실패 경험 반영에 연결된다. Voyager는 1단계의 스킬 검색과 5·6단계의 버전 축적에 가장 직접적으로 연결된다. OSWorld는 4단계의 독립 검증과 실험 초기 상태 복원에 적용하였다.

### 8.2 실험 방법

스킬의 효과는 같은 모델과 도구에서 네 조건을 비교하였다. SK0은 스킬을 제공하지 않고, SK1은 같은 내용을 일반 지침으로 제공한다. SK2는 구조화한 최초 스킬, SK3는 실패 기록을 반영한 개정 스킬을 제공한다. 같은 작업·반복 번호의 네 조건을 하나의 대응 블록으로 묶고 모델 설정, 도구 목록과 초기 상태 해시가 모두 같은 경우만 분석하였다.

작업 성공은 언어 모델의 완료 문장으로 판단하지 않았다. 파일과 앱의 실제 상태가 사전에 정한 완료 조건과 일치해야 성공으로 기록하였다. 성공률과 Wilson 95% 신뢰구간을 보고하고, SK3와 각 기준 조건의 대응 성공 여부는 정확 McNemar 검정과 Holm 보정으로 비교하였다.

## 9. 발표와 논문에서 사용할 표현

발표에서는 “논문의 방법을 그대로 구현했다”라고 설명하면 정확하지 않다. 다음처럼 구분해서 말하는 편이 맞다.

- ReAct의 행동·관찰 반복 구조를 Windows 실행 하네스에 적용했다.
- Toolformer의 API 호출 구조를 참고했지만 모델을 미세조정하지 않았다.
- Reflexion의 피드백 재사용 원리를 실패 기록 기반 개정 초안에 적용했다.
- Voyager의 스킬 저장·검색·개선 개념을 가져왔지만 실행 코드는 저장하지 않고 사람 승인을 추가했다.
- OSWorld의 초기 상태 복원과 실행 기반 평가 원리를 자체 실험에 적용했다.

본 연구의 방법론적 기여는 새 언어 모델 학습법이 아니다. 기존 에이전트 연구의 행동·도구·피드백·스킬 저장 원리를 개인 Windows PC에 맞는 제한된 기능 계약과 승인 가능한 버전 관리로 결합하고, 같은 모델에서 스킬 제공 방식만 바꾸어 평가한 것이다.
