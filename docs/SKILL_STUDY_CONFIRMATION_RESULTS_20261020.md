# Windows 반복 작업에서 스킬 재사용과 개정이 실행 결과에 미치는 영향

## 1. 실험 목적

JAVIS는 Windows에서 수행한 작업의 절차와 판단 기준, 완료 확인 방법을 스킬로 저장하고 다음
요청에서 다시 사용하는 프로그램이다. 파일명이나 현재 경로처럼 실행할 때마다 달라지는 값은
스킬에 넣지 않고, 작업을 시작할 때 다시 확인한다. 실행 결과가 반복해서 실패하면 기존 스킬을
바로 바꾸는 대신 개정 초안을 만들고 사용자가 검토하도록 하였다.

이 실험에서는 같은 언어 모델과 같은 Windows 기능을 사용할 때 스킬 제공 방식에 따라 작업
성공률과 실행 비용이 달라지는지 확인하였다. 비교 조건은 스킬이 없는 경우, 같은 내용을 일반
지침으로 제공한 경우, 최초 스킬을 사용한 경우, 실패 기록을 반영한 개정 스킬을 사용한 경우의
네 가지다. 결과를 확인하기 전에 실행 묶음, 반복 수, 난수 초기값(seed)과 제외 기준을
`docs/SKILL_STUDY_CONFIRMATION_20261020.md`에 기록하였다.

## 2. 프로그램 구성

사용자 요청이 들어오면 프로그램은 승인된 스킬 가운데 관련 항목을 검색한다. 스킬이 있으면 저장된
절차와 판단 규칙을 현재 파일·폴더 상태에 적용하고, 스킬이 없으면 언어 모델이 기본 실행 계획을
만든다. 계획은 등록된 Windows 기능만 사용할 수 있으며, 파일 이동과 앱 실행 결과는 실행기가 아닌
별도의 확인 단계에서 검사한다. 성공 여부와 실행 시간, 언어 모델 호출 수, 토큰 수, 사용자 확인
횟수는 실행에 사용한 스킬 버전과 함께 기록된다.

실험 조건은 표 1과 같다.

**표 1. 스킬 제공 조건**

| 조건 | 제공 정보 |
|---|---|
| SK0 | 스킬 없이 언어 모델과 Windows 기능만 제공 |
| SK1 | 반복 절차를 일반 지침 형태로 제공 |
| SK2 | 절차·동적 입력·판단 규칙·검증 규칙을 포함한 최초 스킬 제공 |
| SK3 | 이전 실패를 반영해 수정한 스킬 제공 |

## 3. 실험 설계

평가 작업은 과제 파일 정리, PDF 열기, 폴더 파일 목록 확인, 확장자별 파일 정리, Explorer에서
지정 폴더 열기의 다섯 종류로 정하였다. 파일을 읽고 이동하는 작업, 읽기 전용 작업, 앱 창을 여는
작업을 함께 포함하기 위한 구성이다. 각 작업을 세 번 반복하고 매 반복에서 SK0~SK3을 한 번씩
실행하여 15개 블록, 60개 관측값을 얻었다.

실행 묶음 식별자는 `developer10`, 조건 순서를 만드는 seed는 `2026102001`로 고정하였다. 같은
블록의 네 조건에는 동일한 모델 ID, 모델 설정, 도구 목록과 초기 파일 상태를 사용하였다. 조건을
실행할 때마다 새 임시 폴더에 같은 실험용 초기 자료(fixture)를 만들었으며, 수집기는 네 조건의 초기 상태 SHA-256이
다르면 해당 입력을 거부하도록 하였다.

성공 여부는 언어 모델이 작성한 답변으로 판정하지 않았다. 파일 정리 작업은 목표 폴더와 파일
내용을, PDF와 Explorer 작업은 등록된 프로그램의 새 창과 대상 파일·폴더를 확인하였다. 각 결과는
별도 JSON 파일에 저장하고 그 SHA-256을 관측 기록과 연결하였다. 실패, 계획 오류와 실행 예산 초과도
제외하지 않았다.

실험을 시작할 때 Edge가 자동 업데이트되어 등록된 실행 파일 해시와 현재 파일의 해시가 다른 것을
확인하였다. 프로그램은 이 상태에서 PDF 작업을 실행하지 않고 중단하였다. 현재 Edge의 전자서명
상태가 유효하고 인증서의 발행자가 등록값과 같은지 확인한 뒤 새 해시를 등록하였다. 실험 실행기도
제품 실행 경로와 같이, 실행 경로와 서명 발행자가 모두 일치하는 경우에만 업데이트된 파일을
허용하도록 수정하였다.

## 4. 평가 지표와 분석 방법

작업 성공률은 전체 실행 가운데 독립 확인을 통과한 실행의 비율로 계산하고 Wilson 방식의 95%
신뢰구간을 함께 구하였다. 실행 시간은 요청 처리 시작부터 결과 확인이 끝날 때까지의 시간이다.
비용 지표로 언어 모델 호출 수와 입력·출력 토큰의 합을 사용하였으며, 별도 확인을 요구한 횟수도
기록하였다.

SK3와 SK0·SK1·SK2의 성공 여부는 같은 작업·반복 번호 안에서 대응시켜 정확 McNemar 검정을
수행하였다. 세 비교에서 생기는 다중 검정 문제는 Holm 방법으로 보정하였다. 유의수준은 양측
0.05로 정하였다.

## 5. 실험 결과

### 5.1 조건별 결과

표 2는 네 조건의 성공률과 실행 비용 평균이다.

**표 2. 조건별 성공률과 실행 비용**

| 조건 | 성공 | 성공률과 95% 신뢰구간 | 평균 시간 | 평균 호출 수 | 평균 토큰 | 평균 확인 횟수 |
|---|---:|---:|---:|---:|---:|---:|
| SK0 | 10/15 | 0.667 (0.417~0.848) | 18.783초 | 2.200 | 3,759.5 | 0.333 |
| SK1 | 12/15 | 0.800 (0.548~0.930) | 18.614초 | 2.467 | 4,268.9 | 0.600 |
| SK2 | 12/15 | 0.800 (0.548~0.930) | 25.742초 | 3.000 | 5,680.9 | 0.533 |
| SK3 | 14/15 | 0.933 (0.702~0.988) | 12.367초 | 1.867 | 3,135.7 | 1.000 |

SK3의 성공률은 SK0보다 0.267, SK1·SK2보다 각각 0.133 높았다. 평균 실행 시간은 SK0보다
34.2%, SK1보다 33.6%, SK2보다 52.0% 짧았다. 평균 토큰 수는 각각 16.6%, 26.6%, 44.8%
적었다. 반면 SK3의 평균 확인 횟수는 1.0회로 네 조건 가운데 가장 많았다. 실행 비용 감소와 사용자
확인 부담이 함께 나타난 결과다.

### 5.2 작업별 결과

**표 3. 작업별 성공 횟수**

| 작업 | SK0 | SK1 | SK2 | SK3 |
|---|---:|---:|---:|---:|
| 과제 파일 정리 | 1/3 | 0/3 | 1/3 | 3/3 |
| PDF 열기 | 2/3 | 3/3 | 3/3 | 2/3 |
| 폴더 파일 목록 확인 | 3/3 | 3/3 | 3/3 | 3/3 |
| 확장자별 파일 정리 | 1/3 | 3/3 | 2/3 | 3/3 |
| Explorer 폴더 열기 | 3/3 | 3/3 | 3/3 | 3/3 |

조건 간 차이는 파일을 분류하고 여러 번 이동해야 하는 두 정리 작업에서 주로 나타났다. 과제 파일
정리에서 SK3는 세 번 모두 성공했지만 SK0과 SK2는 한 번씩, SK1은 한 번도 성공하지 못했다.
확장자별 정리에서는 SK1과 SK3가 세 번 모두 성공하였다.

폴더 목록 확인과 Explorer 폴더 열기는 모든 조건이 성공하였다. 이 두 작업에서는 스킬 제공 여부가
성공률 차이를 만들지 않았다. PDF 열기에서는 SK1과 SK2가 모두 성공한 반면 SK3는 한 번 실패했다.
따라서 개정 스킬의 효과는 모든 작업에서 같은 방향으로 나타나지 않았다.

실패는 모두 12건이었다. 과제 파일 정리에서는 관찰 반복 횟수 소진과 계획 형식 오류가, 확장자별
정리에서는 관찰 루프 오류와 반복 횟수 소진이 발생하였다. PDF 열기의 두 실패는 계획 형식 오류였다.

## 6. 결과 해석

개정 스킬은 전체 평균에서 가장 높은 성공률과 가장 짧은 실행 시간, 가장 적은 호출·토큰 수를
보였다. 특히 파일 분류와 이동처럼 중간 판단과 완료 확인이 반복되는 작업에서는 저장된 절차와
검증 규칙을 다시 사용하는 방식이 실행 계획을 매번 만드는 것보다 도움이 될 가능성이 있었다.

반대로 한 번의 조회나 앱 실행으로 끝나는 작업에서는 네 조건의 성공률이 같거나 SK3도 실패하였다.
이 경우 스킬 검색과 스킬 내용을 입력하는 과정이 추가되므로 성공률의 이점 없이 비용만 늘 수 있다.
SK2의 평균 시간이 가장 길었던 것도 최초 스킬이 항상 효율적이지 않음을 보여준다. 실패 기록을
어떻게 반영했는지와 작업의 복잡도를 함께 고려해야 한다.

SK3의 사용자 확인 횟수가 가장 많았다는 점도 남는다. 위험한 파일 이동을 확인하는 과정이 성공률을
높이는 데 기여했을 수 있으므로, 결과를 완전 자동화의 성능으로 해석해서는 안 된다.

## 7. 실행 기록 검증

통합 자료에는 60개 관측과 60개 결과 근거가 들어 있다. 각 근거 파일의 실제 SHA-256을
무결성 목록(manifest)과 대조한 결과 불일치는 없었다. 관측 파일과 분석 보고서의 SHA-256도
무결성 목록의 기록과 같았다.

- 관측 파일: `9fbc4c4a9fd05b173d11801b1db3f48725df60cbab8424df2c1dc3f5e73ac209`
- 분석 보고서: `84b5480bdbe0e33bf1827323cf69f481c094acddc216a5b7d5787239a97c9d1e`
- manifest: `3a7d03f30a3c4610d4cba7e3f48274a086521bb6364f163ceca5b26e78ce9b12`

다섯 실행기를 같은 인자로 다시 실행했을 때 원장·관측·보고서 15개 파일의 SHA-256은 바뀌지
않았다. 재실행 과정에서 완료된 셀을 다시 수행하지 않았다는 뜻이다. 통합 자료에서 Windows 사용자
절대경로와 NIM API 키 형식의 문자열은 발견되지 않았다.

## 8. 결론

다섯 작업 15블록의 자체 실험에서 SK3는 14회 성공하여 SK0의 10회, SK1·SK2의 12회보다 높은
성공 횟수를 보였다. 평균 실행 시간과 호출·토큰 수도 SK3가 가장 적었다. 차이는 주로 여러 단계의
파일 정리 작업에서 나타났고, 단순 조회와 폴더 열기에서는 성공률 차이가 없었다.

표본 수가 작고 한 대의 개발 PC에서 같은 개발자가 반복한 결과이므로 일반 사용자나 다른 Windows
환경으로 확대할 수 없다. Holm 보정 뒤 유의한 성공률 비교도 없었다. 이 자료는 프로그램의 실험
경로가 실제로 동작하는지와 후속 사용자 실험의 조건을 점검한 결과로 사용한다.

기존 32블록 개발 자료와 이번 15블록 자료는 실행일, 식별자와 seed가 다르다. 두 자료는 각각
보고하며, 결과를 본 뒤 표본 수를 늘린 하나의 확증 실험으로 합치지 않는다. 실제 사용자에 대한
결론에는 연구윤리 절차 확인, 사전에 정한 표본 수와 익명 참가자를 사용한 별도 실험이 필요하다.
