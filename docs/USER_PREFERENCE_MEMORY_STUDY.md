# SKILLA 사용자 선호 기억 사전 검토

상태: 조사 전용, DB·코드 미변경

작성일: 2026-11-18

## 현재 기억 구조에서 이미 가능한 것

`SqliteMemoryRepository`의 semantic 기억은 다음 정보를 저장할 수 있다.

- 영문 소문자로 시작하는 고정 key
- 문자열·정수·실수·참/거짓·null 중 하나인 값
- `explicit_user_instruction` 또는 `verified_task` 출처
- 0~1 신뢰도
- `LOW` 또는 `MEDIUM` 민감도
- 선택적 UTC 만료 시각
- 생성 시각과 마지막 사용 시각

같은 key를 다시 저장하면 같은 ID로 값이 바뀌고, ID로 삭제할 수 있다. DB는 기본 10,000행과
10MB로 제한되며 Windows에서 현재 사용자와 LocalSystem만 접근하도록 ACL을 적용한다. 비밀번호,
API key, bearer token과 private key 형태는 저장 전에 거부한다.

따라서 `좋아하는 음악 장르를 기억해 둬`처럼 사용자가 직접 요청한 낮은 민감도의 단일 선호는
기술적으로 다음과 같은 고정 key로 표현할 수 있다.

```text
preference.music.genre = "발라드"
source = explicit_user_instruction
sensitivity = LOW
expires_at = 사용자가 선택한 만료 시각
```

이 예시는 설계 표현일 뿐이며 현재 DB에 쓰지 않았다.

## 그대로 사용하기 어려운 이유

1. 전체 선호 목록을 안전하게 보여 주는 전용 조회 기능이 없다.
2. 삭제는 memory ID가 필요하고 사용자가 이해할 수 있는 이름별 삭제 화면이 없다.
3. 저장 동의 시각, 동의 문구 버전, 사용 목적, 마지막 재확인 시각을 별도 필드로 보관하지 않는다.
4. `LOW`·`MEDIUM`만 구분하며 건강·금융·가족관계 같은 금지 범주를 의미적으로 판별하지 않는다.
5. credential 정규식은 비밀 값의 일부 형태만 막으며 개인정보 분류기를 대신하지 않는다.
6. 현재 FTS 검색에는 검증된 작업 기억과 파일 경로 기억도 함께 들어갈 수 있어 사용자 선호와
   검색 목적이 섞일 수 있다.
7. 파일 ACL은 다른 일반 사용자의 접근을 줄이지만 DB 값 자체를 암호화하지는 않는다.
8. 원격 NIM에 기억 값을 넘기지 않는다는 전용 대화 경계가 아직 없다.
9. 현재 상태 백업은 skills·trace·trigger·schedule 네 DB만 포함하고 `memory.sqlite3`는 포함하지
   않는다. 선호 기억을 별도 DB로 만들면 백업 제외에 따른 손실 가능성과 백업 포함에 따른 삭제
   잔존 위험 중 어느 정책을 사용할지 명시해야 한다.

## 권장 분리 구조

사용자 선호는 기존 작업 기억에 바로 섞기보다 별도 `conversation_preferences.sqlite3`에 저장하는
편이 안전하다. 실제 구현 시에도 DB 생성은 사용자가 첫 저장을 승인한 순간까지 미룬다.

제안 필드:

| 필드 | 목적 |
|---|---|
| preference_id | 화면에 원문 값을 노출하지 않는 내부 ID |
| key | 허용 목록에 등록된 선호 종류 |
| value_json | 하나의 제한된 scalar 값 |
| category | 음악·말투·호칭·일정 형식 등 허용 범주 |
| sensitivity | LOW 또는 MEDIUM |
| consented_at | 사용자가 저장을 승인한 UTC 시각 |
| consent_version | 화면에 보여 준 동의 문구 버전 |
| expires_at | 자동 만료 시각 |
| last_confirmed_at | 사용자가 마지막으로 유지에 동의한 시각 |
| created_at·updated_at | 생성·변경 시각 |

허용 key는 코드에 고정하고 자유로운 key 생성을 막는다. 초기 허용 예시는 다음 정도로 제한한다.

- `preference.address_name`: 사용자가 원하는 호칭
- `preference.music.genre`: 선호 음악 장르
- `preference.response.length`: 짧게·보통·자세히
- `preference.tts.enabled`: 음성 답변 사용 여부
- `preference.tts.voice`: 설치된 고정 음성 ID

건강, 금융, 비밀번호, 인증 정보, 가족·연애 관계, 정확한 위치, 생체정보는 초기 허용 목록에 넣지
않는다. 자유 형식 일기나 대화 원문도 저장하지 않는다.

## 저장·조회·삭제 흐름

```text
사용자: "발라드 좋아한다고 기억해 둬"
→ 로컬에서 허용 key와 값 후보 생성
→ 화면·음성으로 "음악 장르: 발라드, 90일 저장" 확인
→ 사용자가 승인
→ 로컬 DB 저장
→ 저장 결과를 다시 읽어 key·값 hash·만료 시각 검증

사용자: "내가 뭘 기억하라고 했지?"
→ 로컬 DB에서 허용 key만 조회
→ 로컬 대화 모델에 필요한 값만 전달
→ NVIDIA NIM에는 전송하지 않음

사용자: "발라드 좋아한다는 기억 지워"
→ 삭제 대상 이름과 현재 값 표시
→ 사용자 확인
→ DB와 검색 인덱스 삭제
→ 같은 key를 다시 조회해 없음 검증
```

90일은 구현 확정값이 아니라 화면에서 설명하기 위한 제안 기본값이다. 사용자가 세션 종료 시 삭제,
30일, 90일, 직접 삭제 전까지 중 하나를 고를 수 있어야 한다.

## Windows 저장값 암호화 사전 조사

이 항목은 설계 검토 결과이며 아직 코드와 DB에 적용하지 않았다.

Windows의 DPAPI(Data Protection API)는 별도 암호화 키 파일을 직접 관리하지 않고 현재 Windows
로그온 사용자 정보에 연결해 값을 암호화할 수 있다. Microsoft 문서에 따르면 기본 사용자 범위로
보호한 값은 일반적으로 같은 로그온 자격 증명을 가진 사용자가 같은 컴퓨터에서만 해제할 수 있고,
암호문 변조 확인을 위한 MAC도 포함한다. 따라서 향후 별도 선호 DB를 만든다면 `value_json`의
평문 대신 DPAPI 결과 BLOB을 저장하는 방식이 적합하다.

적용 시 기준은 다음과 같다.

- 현재 사용자 범위 사용
- `CRYPTPROTECT_LOCAL_MACHINE` 미사용: 이 옵션은 같은 PC의 다른 사용자도 해제할 수 있음
- `CRYPTPROTECT_UI_FORBIDDEN` 사용: 백그라운드·음성 실행 중 암호 입력 창이 갑자기 뜨지 않게 함
- 값만 암호화하고 허용 key·범주·만료 시각은 조회 가능한 메타데이터로 유지
- 선호 원문을 FTS나 로그에 저장하지 않고, 목록 화면에서 현재 사용자 권한으로 필요할 때만 해제
- 해제한 평문은 사용 직후 메모리에서 지우고 로그에는 ID·범주·성공 여부만 기록
- 선택적 entropy를 쓰더라도 프로그램에 고정 문자열로 넣는 것을 별도 비밀키로 간주하지 않음

DPAPI는 파일 ACL을 대체하지 않는다. DB에는 현재 사용자와 LocalSystem만 접근하는 ACL을 계속
적용하고, 그 안의 민감한 값만 한 번 더 암호화해야 한다. 또한 Windows 계정·사용자 프로필이나
DPAPI master key를 잃으면 백업 DB만으로 복구하지 못할 수 있다. 그러므로 향후 백업 기능은 다음
둘 중 하나를 사용자에게 명시적으로 선택하게 해야 한다.

1. 기기 안에서만 복원: 현재 사용자 DPAPI 암호문을 그대로 백업하고 같은 계정·프로필에서만 복원
2. 이동 가능한 내보내기: 사용자가 정한 별도 암호로 다시 암호화한 내보내기 파일을 생성

초기 구현 범위에는 1번만 포함하고, 계정 변경·Windows 재설치·다른 PC 이전은 지원하지 않는다고
관리 화면에 표시하는 편이 안전하다. 2번은 별도 비밀번호 처리와 복구 검증이 필요하므로 독립된
기능으로 시험해야 한다.

공식 근거:

- Microsoft `CryptProtectData`: 현재 사용자 또는 컴퓨터에 연결한 암호화 범위와 플래그 설명
- Microsoft `CryptUnprotectData`: 복호화, 무결성 검사, 비대화형 플래그 설명

## 도입 전 합격 기준

- 승인 전 DB 생성과 저장 0건
- 허용 목록 밖 key 저장 0건
- 금지 범주 저장 0건
- 원격 NIM 요청에 선호 값 포함 0건
- 목록·수정·삭제·전체 초기화 기능 모두 제공
- 삭제 뒤 현재 DB의 key·FTS에서 재조회 0건
- 선호 백업을 제공한다면 삭제 시 백업 보존기간과 완전 삭제 시점을 사용자에게 표시
- 만료 뒤 자동 purge와 재조회 0건
- DB 파일 사용자 전용 ACL 확인
- DB의 선호 값이 평문 검색으로 발견되지 않고 현재 사용자 DPAPI로만 해제됨
- 다른 Windows 일반 사용자에서 같은 선호 값 해제 실패
- 사용자 프로필·자격 증명 손실 시 복구 불가 안내와 백업 정책 표시
- 손상 DB에서 시작 차단 또는 검증된 백업 복원
- 감사 로그에는 값 대신 ID·범주·결과만 기록

## 결론

현재 semantic memory는 단일 선호를 담을 기본 자료형과 삭제 기능을 갖고 있지만, 사용자에게 보이는
동의·목록·삭제 관리와 원격 비전송 경계가 부족하다. 유대감 기능을 구현한다면 기존 DB에 값을 바로
추가하는 방식이 아니라, 허용 key가 고정된 별도 로컬 선호 저장소와 관리 화면을 먼저 만드는 것이
적절하다.
